# About

개발하다 보면 코드는 남아 있어도, 왜 그렇게 만들었는지는 잊기 쉽습니다.
어떤 문제를 풀고 있었는지, 다른 방법 대신 이 구조를 고른 이유가 무엇이었는지는 코드만으로 알기 어렵습니다.

**Origemite Archive는 그 과정과 판단을 함께 남기는 개인 엔지니어링 아카이브입니다.**
공부하며 적어 둔 메모부터 직접 구현한 코드, 운영 중 겪은 문제와 개선 경험까지 모으고 있습니다.
다음에 비슷한 문제를 만났을 때 다시 꺼내 보고, 다른 사람이 읽어도 자신의 상황에 맞게 활용할 수 있는 기록을 지향합니다.

## 이곳에 담는 이야기

백엔드 개발을 중심으로 인프라 구성과 운영, 설계와 테스트를 다룹니다.
개별 기술의 사용법뿐 아니라, 여러 기술을 연결해 하나의 시스템으로 만드는 과정에도 관심이 있습니다.

| 영역 | 기록하는 내용 |
| --- | --- |
| [Knowledge](/docs/knowledge/) | 기술 개념과 사용 방법, 코드 예제, 개발하며 정리한 기준 |
| [Patterns](/docs/patterns/index) | 반복되는 문제를 푸는 패턴과 구현 예제 |
| [Architecture](/docs/architecture/) | 시스템 구성, 계층의 책임, 데이터와 요청이 흐르는 방식 |
| [Decisions](/docs/decisions/) | 기술과 구조를 선택한 이유, 검토한 대안과 그 결과 |
| [Postmortems](/docs/postmortems/) | 프로젝트에서 겪은 문제, 장애 대응과 개선 경험 |
| [Blog](/blog) | 개발 과정에서의 고민과 변화, 정리해 두고 싶은 이야기 |
| [Harness](/docs/harness/) | AI와 함께 개발할 때 사용하는 작업 기준과 코드, 테스트 템플릿 |

개념을 설명하는 예제와 실제 프로젝트에 적용한 경험은 구분해서 적습니다.
같은 기술을 사용하더라도 당시의 요구사항과 제약에 따라 선택이 달라질 수 있기 때문입니다.

## AI와 함께 개발하는 방식

AI를 활용하면서 가장 중요하게 생각하는 것은 **제가 읽고 판단하기 쉬운 코드를 유지하는 일**입니다.
익숙한 구조와 일관된 이름으로 작성된 코드는 의도를 따라가기 쉽고, 잘못된 부분도 빠르게 찾을 수 있습니다.
코드 컨벤션과 템플릿을 정리하는 이유도 여기에 있습니다.

작업 범위와 계층의 책임, 코드 스타일, 확인해야 할 결과를 먼저 정합니다.
그 안에서 구현 방법과 작업 순서는 AI가 상황에 맞게 선택하도록 둡니다.
작은 수정은 간단하게 진행하고, 여러 계약이나 복잡한 흐름이 얽힌 변경은 그에 맞는 검토와 테스트를 더합니다.

하네스에는 이러한 기준을 문서로 정리해 두었습니다.
필요한 문서와 기존 구현을 찾아 참고하고, 코드와 테스트를 함께 확인하는 데 사용합니다.
역할을 나누어 두었지만, 모든 작업에 여러 에이전트를 실행하는 방식은 아닙니다.

테스트 결과와 실제 변경 내용을 확인하고, 최종적으로 코드를 받아들이는 판단은 개발자가 합니다.
모델이나 도구가 바뀌어도 이 기준은 계속 다듬어 사용할 수 있도록 관리하고 있습니다.

## 기록을 오래 쓰기 위해

글과 예제의 원본은 Markdown으로 작성하고 Git으로 관리합니다.
Docusaurus는 이 기록들을 읽고 찾아보기 위한 사이트입니다.
프로젝트나 사용하는 도구가 바뀌더라도, 쌓아 둔 지식과 판단의 근거를 이어서 활용하려고 합니다.

오래된 메모를 옮긴 글도 있고, 최근의 코드와 경험을 바탕으로 다시 쓰는 글도 있습니다.
설명이 부족하거나 지금의 생각과 달라진 부분은 확인하면서 고쳐 나갑니다.
새로운 내용을 추가하는 만큼, 기존 기록을 다시 읽고 다듬는 일도 이 아카이브의 일부입니다.
