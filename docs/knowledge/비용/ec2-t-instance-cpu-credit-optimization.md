# AWS t 계열 인스턴스 운영기 (폭주 → 배치 튜닝 → 시분할 적용 → 안정화)

## 1. 배경

IoT 기반 시스템을 운영하면서 다음과 같은 구성을 사용하고 있었다.

- EC2: t3.medium
- Docker Compose 기반 서비스 운영
- Jenkins 기반 CI/CD
- 센서 데이터 수신 + 배치 집계 구조

비용 절감을 위해 t 계열 인스턴스를 선택했다.

---

## 2. 문제 상황

배치 작업과 CI/CD가 동시에 실행되면서 CPU 사용률이 장시간 90\~100%에 근접했다.

CloudWatch 기준:

- CPU 사용률: 90\~100%
- CPUCreditBalance: 576 → 0
- CPUCreditUsage: 지속 발생

결과적으로 크레딧이 완전히 소진되었고, 이후 구간에서는 초과 사용이 발생했다.

![CPU 크레딧 고갈](/img/aws/ec2-t-instance/cpu-credit-exhaustion.png)

---

## 3. 원인

문제는 단순한 CPU 사용 증가가 아니라 부하가 한 번에 몰린 구조였다.

배치 처리, CI/CD 빌드, 실시간 요청 처리가 동시에 수행되면서 CPU를 지속적으로 점유하게 된 것이 원인이었다.

특히 배치가 한 번에 많은 데이터를 처리하는 방식이어서 부하가 길게 유지되는 구조였다.

---

## 4. 대응

### 배치 로직 수정

기존에는 하루 단위 데이터를 한 번에 처리하는 방식이었다.

이 구조를 다음과 같이 변경했다.

- 재집계 구조는 유지
- 처리 범위를 나눠서 실행
- 반복 실행 가능한 구조로 변경

---

### 시분할 적용

배치를 시간 단위로 나눠 실행하도록 수정했다.

예를 들어 하루 데이터를 다음과 같이 분할했다.

- 00:00 \~ 06:00
- 06:00 \~ 12:00
- 12:00 \~ 18:00
- 18:00 \~ 24:00

또는 상황에 따라 1시간 단위로 더 세분화할 수 있도록 구성했다.

---

### 실행 간격 분산

- Daily Batch → 하루 4회
- Monthly Batch → 하루 1회

한 번에 몰리는 부하를 줄이고, CPU 사용량이 분산되도록 조정했다.

---

### 부하 제어

- 동시 실행 제한
- 배치 간 간격 확보
- 트랜잭션 범위 축소

---

### Docker 리소스 관리

빌드 시 누적되는 이미지를 정리하도록 설정했다.

```bash
docker image prune -f
```

---

## 5. 결과

튜닝 이후 상태는 다음과 같다.

- CPU 사용률: 1\~5%
- CPUCreditUsage: 거의 없음
- CPUCreditBalance: 회복 시작
- 서비스 정상 동작

CPU 사용률이 낮게 유지되면서 크레딧이 다시 쌓이는 상태로 전환되었다.

![튜닝 후 회복](/img/aws/ec2-t-instance/cpu-credit-recovery.png)

---

## 6. t 계열 인스턴스 특징

t 계열은 크레딧 기반으로 동작한다.

- baseline 이하에서는 크레딧이 적립된다
- burst 시 크레딧을 사용한다
- 지속적인 부하에서는 크레딧이 고갈된다

크레딧은 최대치까지만 존재하고, 0이 된 이후에는 더 줄어들지 않는다. 대신 초과 사용 구간으로 넘어간다.

회복은 항상 0에서 최대치까지 동일한 기준으로 진행된다.

---

## 7. 회복 과정

실제 CloudWatch에서는 다음과 같은 형태로 나타난다.

- 일정 시간 동안 0 유지
- 이후 갑자기 증가

초과 사용 구간을 지나고 나서야 크레딧 적립이 눈에 보이기 시작한다.

---

## 8. 정리

이번 이슈의 핵심은 CPU가 아니라 배치 구조였다.

한 번에 처리하는 방식은 t 계열 인스턴스와 맞지 않는다.
데이터를 나눠서 처리하고, 실행 시점을 분산시키는 것이 중요하다.

---

## 9. 결론

t 계열 인스턴스는 비용 효율적인 선택이지만, 구조를 이해하고 사용해야 한다.

특히 배치 작업은 한 번에 처리하는 방식이 아니라, 나눠서 처리하는 구조가 필요하다.
