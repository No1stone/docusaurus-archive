# PHP 보안 취약점 대응을 위한 런타임 및 애플리케이션 업그레이드

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 결정일 | 2026-10-25 |
| 대상 | AWS EC2, Docker Compose, Nextcloud |
| 변경 범위 | PHP 8.3 → 8.5, Nextcloud 30 → 35 |
| 목적 | 보안 패치 적용 및 런타임 지원 버전 현대화 |

## 1. Context — 배경

운영 중인 Nextcloud 환경은 PHP 8.3 기반으로 구성되어 있었습니다.

2026년 10월 PHP 보안 취약점 대응 필요성이 제기되면서 기존 런타임과 애플리케이션의 유지보수 상태를 검토했습니다.

당초 목표는 PHP 취약점 패치였지만, 점검 과정에서 다음 문제를 함께 고려해야 했습니다.

- PHP 런타임의 보안 패치 수준
- 기존 Nextcloud 메이저 버전의 지원 상태
- Nextcloud와 PHP 버전 간 호환성
- 설치된 확장 애플리케이션의 호환성
- 데이터베이스 스키마 마이그레이션
- 소규모 EC2 환경에서의 업그레이드 안정성

핵심 문제는 **PHP가 독립적인 실행 환경이 아니라 Nextcloud 공식 Docker 이미지의 구성요소**라는 점이었습니다.

PHP만 교체하는 방식은 기존 애플리케이션과 확장 모듈의 호환성 문제를 유발할 수 있었습니다.

따라서 런타임 보안 패치와 애플리케이션 업그레이드를 하나의 변경 작업으로 다루기로 했습니다.

## 2. Decision Drivers — 의사결정 기준

이번 결정에서 우선순위로 삼은 기준은 다음과 같습니다.

1. 보안 패치가 반영된 PHP 런타임 확보
2. Nextcloud 공식 이미지 기반 운영 유지
3. 애플리케이션과 PHP 간 호환성 확보
4. 기존 데이터 및 설정 보존
5. 다른 Docker 서비스에 미치는 영향 최소화
6. 각 단계의 실패 여부를 확인할 수 있는 업그레이드 방식

## 3. Considered Options — 검토한 대안

### Option A. 기존 Nextcloud에서 PHP만 교체

기존 Nextcloud 30을 유지하고 PHP 런타임만 교체하는 방식입니다.

**장점**

- 애플리케이션 메이저 업그레이드를 피할 수 있음
- 변경 대상이 PHP 런타임에 집중됨

**단점**

- 공식 이미지의 기본 구성을 벗어날 수 있음
- PHP 확장 모듈 및 애플리케이션 호환성 검증 필요
- Nextcloud 자체의 보안 및 유지보수 문제는 별도로 남음
- 향후 이미지 업데이트 관리가 복잡해질 가능성

**결론: 채택하지 않음.**

### Option B. 최신 Nextcloud 이미지로 직접 교체

기존 Nextcloud 30에서 35로 이미지 태그를 즉시 변경하는 방식입니다.

**장점**

- 변경 절차가 단순함
- 최신 이미지로 빠르게 전환할 수 있음

**단점**

- Nextcloud의 메이저 버전 순차 업그레이드 요구사항과 충돌
- 중간 버전의 데이터베이스 마이그레이션을 건너뛸 위험
- 업그레이드 실패 시 원인 분석이 어려움

**결론: 채택하지 않음.**

### Option C. Nextcloud 메이저 버전 순차 업그레이드

공식 Docker 이미지를 사용하면서 각 메이저 버전을 순서대로 업그레이드하는 방식입니다.

```text
Nextcloud 30
     ↓
Nextcloud 31
     ↓
Nextcloud 32
     ↓
Nextcloud 33
     ↓
Nextcloud 34
     ↓
Nextcloud 35
```

**장점**

- 공식 이미지 기반 운영 유지
- 버전별 DB 마이그레이션 수행
- 단계별 정상 상태 검증 가능
- PHP 런타임도 호환되는 버전으로 함께 갱신
- 장기적인 유지보수 부담 감소

**단점**

- 여러 번의 이미지 다운로드 및 컨테이너 재생성 필요
- 애플리케이션 업데이트와 무결성 검사에 시간 소요
- 각 단계의 호환성 검증 필요

**결론: 채택.**

## 4. Decision — 최종 결정

**Option C: Nextcloud 공식 Docker 이미지 기반 순차 업그레이드를 채택합니다.**

구체적인 실행 원칙은 다음과 같습니다.

- 메이저 버전을 건너뛰지 않습니다.
- 공식 Docker 이미지의 PHP 런타임을 사용합니다.
- Nextcloud 컨테이너만 재생성합니다.
- 데이터 볼륨은 유지합니다.
- DB 마이그레이션 완료 여부를 검증합니다.
- 최종 업그레이드 이후 서비스 정상 동작을 확인합니다.
- 이미지 정리는 업그레이드 완료 후 진행합니다.

## 5. Implementation — 적용 결과

2026년 10월 25일 순차 업그레이드를 진행했습니다.

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| Nextcloud | 30.0.17 | 35.0.2 |
| PHP | 8.3.28 | 8.5.12 |
| Apache | 기존 이미지 | 2.4.69 |
| DB 마이그레이션 | 정상 | 정상 |
| 서비스 동작 | 정상 | 정상 확인 |

최종 상태 확인 결과:

```text
installed: true
version: 35.0.2.2
versionstring: 35.0.2
maintenance: true
needsDbUpgrade: false
```

위 상태는 최종 마이그레이션 직후의 결과입니다.
이후 서비스 정상 동작을 별도로 확인했습니다.

## 6. Consequences — 결정에 따른 영향

### 긍정적 영향

**1. 보안 유지보수 기반 개선**

기존 PHP 8.3 및 Nextcloud 30 기반 환경을 새로운 지원 버전으로 전환했습니다.

**2. 공식 이미지 기반 운영 유지**

커스텀 PHP 런타임을 별도로 유지하지 않아도 됩니다.

**3. 데이터베이스 정합성 검증**

각 메이저 업그레이드에서 `needsDbUpgrade: false`를 확인했습니다.

**4. 운영 구조의 단순화**

향후 업데이트에서도 동일한 Docker Compose 배포 방식을 사용할 수 있습니다.

### 부정적 영향 및 잔여 위험

- 여러 차례의 이미지 다운로드로 작업 시간 증가
- 소규모 EC2 환경에서 업데이트 처리 시간 증가
- 앱별 호환성 및 설정 검증 필요
- 이미지 내부 OS 패키지 취약점은 별도 검사 필요
- 백업 없이 진행한 작업이므로 장애 발생 시 복구 위험 존재

## 7. Verification — 검증 기준

이번 변경의 검증 기준은 다음과 같습니다.

| 검증 항목 | 결과 |
|---|---|
| Nextcloud 35 실행 | Pass |
| PHP 8.5.12 적용 | Pass |
| DB 마이그레이션 완료 | Pass |
| Apache 정상 실행 | Pass |
| Nextcloud 서비스 접근 | Pass |
| 전체 앱 기능 검증 | 추가 점검 |
| 컨테이너 취약점 스캔 | 추가 점검 |

최신 런타임 적용과 모든 보안 취약점 제거는 동일한 의미가 아닙니다.

따라서 향후 이미지 취약점 스캔과 정기적인 보안 공지 확인을 별도 운영 항목으로 관리합니다.

## 8. Follow-up Actions — 후속 작업

- Nextcloud 및 PHP 보안 공지 정기 확인
- 설치된 앱 호환성 및 업데이트 상태 점검
- 컨테이너 이미지 취약점 스캔
- Docker 이미지 업데이트 자동화 검토
- 데이터 백업 및 복구 절차 정비

## Conclusion

이번 의사결정의 핵심은 단순히 PHP 버전을 높이는 것이 아니었습니다.

**보안 패치가 필요한 상황에서 기존 시스템의 지원 범위와 호환성을 함께 고려해, 공식적으로 유지보수 가능한 구성으로 전환하는 것**이었습니다.

PHP 단독 교체보다 작업량은 증가했지만, 애플리케이션과 런타임을 함께 현대화함으로써 향후 운영 부담을 줄일 수 있는 방향을 선택했습니다.
