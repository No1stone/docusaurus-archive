# 아카이브 화면은 Docusaurus로 둡니다

Origemite Archive의 문서 사이트는 Docusaurus로 구성합니다.
Markdown 원본은 그대로 관리하고, 사람은 사이트에서 문서를 탐색하며 AI는 필요한 원본 파일을 읽도록 역할을 나눕니다.
문서 탐색 기능을 직접 만드는 부담을 줄이면서, 필요한 화면은 익숙한 React로 구성할 수 있다는 점을 고려했습니다.

## 배경

[ADR-0001](./ADR-0001-markdown-git-as-engineering-source-of-truth.md)에서 결정과 개발 기준의 원본을 Git 안의 Markdown으로 정했습니다.
파일만으로도 기록을 관리할 수 있지만, 문서가 늘어나면 사람에게는 목록과 목차를 따라 읽을 화면이 필요합니다.
외부 독자도 저장소 구조나 AI와의 대화를 모르는 상태에서 내용을 이해할 수 있어야 합니다.

한편 AI가 자료를 활용하기 위해 반드시 사이트를 거칠 필요는 없습니다.
접근 가능한 저장소에서 필요한 Markdown과 코드 템플릿을 읽도록 하면 됩니다.
따라서 사이트 선택에서는 문서를 읽는 경험과 화면 유지보수 비용에 집중했습니다.

## 선택 기준

- Markdown 문서를 원본으로 유지할 수 있어야 합니다.
- 문서 목록, 사이드바, 본문 목차를 제공해야 합니다.
- 소개 페이지처럼 문서 외의 화면을 추가할 수 있어야 합니다.
- 정적 파일로 빌드해 현재 배포 환경에서 운영할 수 있어야 합니다.
- 사이트 구현이 바뀌어도 문서의 결정 이유와 기준을 읽을 수 있어야 합니다.

## 결정

Docusaurus의 classic preset과 docs 기능을 사용합니다.
현재는 문서 트리 중심으로 아카이브를 구성하고 블로그 기능은 사용하지 않습니다.

### 문서 탐색은 Docusaurus에 맡깁니다

`docs/`의 문서를 `/docs` 아래에 제공하고, 폴더 구조를 기준으로 사이드바를 생성합니다.
제목과 설명, 목록 순서 같은 메타데이터는 문서를 찾고 읽는 데 사용합니다.
계층의 책임이나 규칙의 적용 조건처럼 구현에 필요한 내용은 본문에 작성합니다.

| 위치 | 역할 |
|---|---|
| `docs/` | ADR, Knowledge, 하네스 안내 등 문서 원본 |
| `docs/harness/templates/` | 문서와 함께 관리하는 구현 및 테스트 템플릿 |
| `sidebars.ts`, `_category_.json` | 사이트의 문서 탐색 구성 |
| `src/pages/` | 홈, About 등 별도 화면 |
| `docusaurus.config.ts` | 사이트 주소, 메뉴, 플러그인 설정 |

### 필요한 화면은 React로 구성합니다

아카이브에는 문서 본문 외에도 홈과 About 같은 화면이 필요합니다.
Docusaurus에서는 React 컴포넌트로 이러한 페이지를 작성할 수 있습니다.
익숙한 기술로 문서 사이트와 소개 화면을 함께 관리할 수 있다는 점이 선택의 이유였습니다.

### AI의 문서 활용은 파일 접근으로 연결합니다

Docusaurus는 AI 에이전트의 실행을 담당하지 않습니다.
다른 프로젝트에서 하네스를 활용할 때는 아카이브 파일에 대한 접근과 진입 규칙을 별도로 연결해야 합니다.

```text
Git으로 관리하는 Markdown과 코드 템플릿
  ├─ Docusaurus 빌드 → 사람이 읽는 문서 사이트
  └─ 하네스 진입 규칙 → AI가 필요한 파일만 선택해 작업
```

저장소를 연결했다는 이유만으로 모든 문서가 자동 적용되는 것은 아닙니다.
에이전트가 어떤 진입 문서를 읽고, 어떤 조건에서 원셋이나 관련 기준을 선택하는지 안내해야 합니다.
제품별 연결 방법은 하네스의 진입 문서에서 관리합니다.

## 검토한 대안

| 대안 | 검토 내용 |
|---|---|
| MkDocs Material | 문서 중심 사이트에 적합한 대안입니다. 이번에는 React 기반 화면 구성과 기존 JavaScript 작업 환경을 우선했습니다 |
| VitePress | Markdown 문서 사이트를 구성할 수 있습니다. 화면 확장에 사용하는 Vue보다 익숙한 React를 선택했습니다 |
| Next.js 등으로 직접 구현 | 화면을 자유롭게 설계할 수 있지만 문서 탐색과 렌더링 구성을 직접 관리해야 합니다 |
| 호스팅형 문서 서비스 | 편집과 운영을 맡길 수 있지만, 이번에는 Git 원본과 현재 정적 배포 흐름을 직접 유지하기로 했습니다 |

다른 도구에서 같은 요구를 해결할 수 없다는 판단은 아닙니다.
문서 기능을 재사용하면서 React로 필요한 부분을 확장하는 방식이 현재 작업 환경에 적합했습니다.

## 운영 방식과 제약

현재는 `main`에 변경을 푸시하면 GitHub Actions가 사이트를 빌드하고 S3에 배포한 뒤 CloudFront 캐시를 갱신합니다.
문서 수정과 사이트 배포를 Git 변경 흐름 안에서 관리합니다.

Docusaurus를 사용해도 글의 품질과 문서 간 일관성은 직접 관리해야 합니다.
검색과 피드 같은 기능도 실제 필요에 따라 별도로 구성해야 하며, 사이트를 만들었다는 이유만으로 모두 제공되는 것은 아닙니다.

MDX와 React를 본문에 많이 사용하면 다른 도구로 옮길 때 수정할 부분이 늘어납니다.
일반 문서는 Markdown 중심으로 작성하고, 사이트에만 필요한 표현은 필요한 범위에서 사용합니다.
