# 원본은 Git 안의 Markdown으로 둡니다

개발하면서 내린 결정과 그 이유를 Git으로 관리하는 Markdown 문서에 남깁니다.
사람은 이 기록을 설계와 리뷰의 근거로 사용하고, AI는 작업에 필요한 기준을 찾아 적용합니다.
대화가 바뀌거나 다른 프로젝트를 시작해도 같은 설명과 판단을 처음부터 반복하지 않기 위한 선택입니다.

## 배경

프로젝트에서 정한 계층의 책임이나 코드 작성 방식은 코드만 보고 모두 이해하기 어렵습니다.
결정의 이유가 당시 대화와 기억에만 남아 있으면, 시간이 지난 뒤에는 왜 그렇게 구현했는지 다시 추측해야 합니다.
AI에게 작업을 맡길 때도 같은 문제가 생겼습니다.
매번 프롬프트에 기준을 다시 설명했고, 설명에서 빠진 부분이나 표현의 차이에 따라 구현 결과가 달라졌습니다.

필요했던 것은 문서를 많이 쌓는 공간보다, 이전에 정한 기준과 그 이유를 다시 찾아 쓸 수 있는 원본이었습니다.
사람과 AI가 같은 기록을 참고하고, 기준이 바뀌면 변경 이유도 함께 확인할 수 있어야 했습니다.

## 결정

Origemite Archive의 문서 원본은 Markdown으로 작성하고 Git으로 관리합니다.
구현 템플릿은 실제 코드 파일로 함께 보관합니다.
사람에게 보여 주는 사이트와 AI가 사용하는 도구는 이 원본을 읽는 수단으로 둡니다.

이 문서에서 SSOT(Single Source of Truth, 단일 진실 원천)는 아카이브가 관리하는 공통 결정과 기준의 원본을 뜻합니다.
프로젝트 코드나 개별 저장소의 명세까지 이 아카이브가 대신한다는 의미는 아닙니다.
실제 작업에서는 대상 저장소의 규칙과 현재 구현을 먼저 확인합니다.

### 결정, 기준, 실행 예제를 연결합니다

문서는 목적에 따라 나누되, 관련 기록을 연결해 같은 내용을 처음부터 설명하지 않도록 합니다.

| 기록 | 남기는 내용 | 활용하는 상황 |
|---|---|---|
| ADR | 무엇을 선택했고 왜 선택했는지 | 결정을 이해하거나 다시 검토할 때 |
| Knowledge | 현재 사용하는 개념과 책임, 적용 범위 | 구현과 리뷰의 기준이 필요할 때 |
| Template | 기준을 반영한 구현과 테스트 예제 | 반복 구조를 복사하고 차이만 채울 때 |
| Orchestration | 필요한 자료와 템플릿, 작업 순서와 검증 | 반복 작업을 같은 절차로 실행할 때 |
| 작업 기록 | 실제 변경 내용과 검증 결과 | 작업의 경과와 남은 문제를 확인할 때 |

모든 경험을 위 순서대로 문서화할 필요는 없습니다.
반복해서 참고할 가치가 있는 내용을 골라 남기고, 이유와 실행 예제가 필요한 경우에 서로 연결합니다.

### 사람과 AI는 같은 원본을 참고합니다

사람은 사이트나 편집기에서 문서를 읽고, AI는 작업에 필요한 파일을 선택해서 읽습니다.
전체 아카이브를 매번 컨텍스트에 넣는 대신, 진입 문서에서 필요한 규칙과 템플릿으로 이동하도록 구성합니다.

예를 들어 API 한 세트를 추가할 때는 관련 원셋을 선택하고 구현, 테스트, E2E 템플릿을 재사용합니다.
설계 의도가 불명확할 때만 연결된 Knowledge와 ADR을 더 확인합니다.

공통 기준을 변경하는 권한은 별도로 관리합니다.
AI는 작업 중 발견한 문제와 개선안을 제안할 수 있지만, Knowledge와 템플릿 등 공통 기준은 사용자가 승인한 범위에서 수정합니다.
작업 중의 판단 하나가 자동으로 전체 규칙이 되지 않도록 하기 위한 경계입니다.

## Markdown과 Git을 선택한 이유

Markdown은 편집기와 파일 읽기 도구로 내용을 확인할 수 있는 평문입니다.
문서를 작은 단위로 나누고 상대 경로로 연결할 수 있어, 사람과 AI가 필요한 부분만 찾아 읽는 방식에 맞았습니다.

Git은 변경 전후의 차이와 시점을 남깁니다.
ADR에는 결정의 배경을 기록하고 커밋에는 실제 변경을 남기면, 기준이 어떻게 달라졌는지 함께 확인할 수 있습니다.
다만 변경 이유가 자동으로 기록되는 것은 아니므로 문서와 커밋 메시지를 작성하는 책임은 남습니다.

원본을 파일로 보관하면 읽기 화면이나 AI 제품을 바꿀 때도 콘텐츠를 재사용하기 쉽습니다.
Docusaurus를 선택한 이유는 [ADR-0002](/docs/decisions/adr-0002)에서 다룹니다.

## 검토한 대안

| 대안 | 장점 | 이번 선택에서 고려한 점 |
|---|---|---|
| 위키 또는 CMS | 브라우저에서 편집하고 협업하기 편합니다 | 파일 기반 코드 작업과 문서 변경을 같은 Git 흐름에서 관리하고 싶었습니다 |
| AI 제품의 지식 저장소 | 해당 제품에서 자료를 활용하기 편합니다 | 여러 에이전트가 공통으로 참조할 독립된 원본이 필요했습니다 |
| 대화와 프롬프트에만 기록 | 바로 시작할 수 있습니다 | 최신 기준과 결정 이유를 다시 찾고 재사용하기 어렵습니다 |

이 도구들도 원본을 관리하는 수단이 될 수 있습니다.
이번에는 로컬 파일과 Git을 중심으로 개발하는 작업 방식에 Markdown이 잘 맞는다고 판단했습니다.

## 결과와 제약

결정과 기준을 대화 밖에 남겨 다음 작업에서 재사용할 수 있게 되었습니다.
템플릿을 통해 반복적인 설명과 코드 생성을 줄이고, 사람도 변경된 코드가 어떤 기준을 따르는지 확인할 수 있습니다.

대신 문서와 실제 구현이 어긋나지 않도록 관리해야 합니다.
오래된 내용을 계속 읽게 하거나 같은 기준을 여러 문서에 중복하면 원본을 정한 효과가 줄어듭니다.
현재 기준과 과거 기록을 구분하고, 변경할 때 관련 문서의 일치 여부를 확인합니다.

사이트 전용 메타데이터는 탐색과 표시에 사용합니다.
설계 의도와 적용 범위는 문서 본문에 남겨, 사이트 없이 파일을 읽어도 이해할 수 있도록 합니다.
