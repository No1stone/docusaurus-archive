# AI Harness — 참고 자료와 적용 원칙

## 도입 배경

AI로 구현하는 속도는 빨라졌지만, 작업마다 코드 구조가 달라지거나 요청하지 않은 문서까지 수정하는 일이 있었습니다. 반대로 규칙을 늘리면 간단한 작업에도 탐색과 검토가 반복되어 시간과 토큰이 소비됐습니다.

이를 줄이기 위해 코드 컨벤션과 템플릿을 기준으로 구현하고, 작업 규모에 맞춰 필요한 절차만 적용하도록 하네스를 구성했습니다.

아래 자료는 현재 운영 방식을 정리하고 개선하는 데 참고했습니다. 기존 구성을 모두 해당 자료에서 가져온 것은 아니며, 공통된 개념과 프로젝트에서 직접 정한 운영 방식을 구분합니다.

## 프로젝트에 맞춰 정한 운영 방식

| 운영 방식 | 적용 기준 |
|---|---|
| **템플릿 기반 원셋** | 구현부터 테스트·Controller API E2E까지 재사용 가능한 구조를 복사하고 차이만 반영 |
| **작업 규모에 따른 실행** | 작은 작업은 단일 에이전트가 수행하고, 필요한 경우에만 역할을 분리 |
| **요청 범위 준수** | 질문은 읽기와 답변으로 처리하고, 명시적으로 요청한 수정은 재확인 없이 진행 |
| **검증 범위 조절** | 변경된 동작·계약·위험에 맞는 검증을 선택하며, 토큰 절약을 이유로 필요한 검증을 생략하지 않음 |
| **세션 분리** | 구조적인 개발은 하네스 적용 세션에서, 간단한 질문과 확인은 일반 세션에서 수행 |
| **공통 원칙과 저장소 규칙 분리** | 공통 하네스는 행동 원칙을 관리하고, 도메인·실행 환경·구현 패턴은 저장소에서 관리 |

이 운영 방식은 참고 자료를 그대로 복제한 구성이 아니라, 실제 작업에서 발생한 문제를 바탕으로 조정한 것입니다.

## 하네스 개선과 평가

하네스도 고정된 규칙으로 두지 않고, 실제 실패 사례를 바탕으로 개선합니다. 에이전트가 개선안을 제안하면 사람이 검토한 뒤 반영하고, 기존에 잘되던 행동이 유지되는지 확인합니다.

| 평가 요청 | 기대하는 행동 |
|---|---|
| “패키지순으로 알려줘” | 필요한 코드를 확인하고 채팅으로만 답변 |
| “drawio도 맞춰줘” | 승인된 범위의 다이어그램 수정 |
| “반환 타입을 구체적인 DTO로 바꿔줘” | 관련 구현과 계약을 확인하고 필요한 테스트 수행 |
| “템플릿으로 CRUD 원셋을 만들어줘” | 템플릿 재사용, 도메인 차이 반영, 테스트·E2E 검증 |
| “현재 상태만 확인해 줘” | 상태를 설명하고 불필요한 문서·기록 수정 생략 |

평가는 답변 문구가 같은지보다 실제 변경 범위와 검증 결과를 중심으로 합니다. 반복 실행에서 요구사항 충족 여부, 불필요한 수정, 작업 시간과 토큰 사용을 함께 비교합니다.

현재는 경량화 규칙의 반영과 문구 충돌 검토까지 진행했습니다. 실제 행동 개선과 토큰 절감 효과는 비교 실행으로 확인할 단계입니다.
