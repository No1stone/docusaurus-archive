# 구현 전 통과 기준

> **개요:** 구현 전에 기대 결과와 완료 기준을 정합니다.
> 모든 작업에 테스트 코드 선작성이나 실패, 통과, 정리를 강제하지 않습니다.
> 완료는 테스트 통과만으로 판단하지 않습니다.

## 실행

누가 확인하는지는 [`implement.md`](./implement.md)입니다.
기본적으로 한 에이전트가 기준을 정하고 검증합니다.

기준은 구현 전에 정합니다.
템플릿에 있는 기준은 재사용하고, 이번 작업의 차이만 추가합니다.
분량은 작업 복잡도에 맞춥니다.

## 작업별 기본 방식

| 작업 | 기본 방식 |
|---|---|
| 기존 템플릿 기반 CRUD | 기존 기준 재사용, 구현 및 관련 테스트 |
| 버그 수정 | 가능한 경우 재현 테스트 먼저 작성, 수정 후 회귀 확인 |
| 복잡한 업무 판단 | 작은 테스트부터 실패, 통과, 정리 반복 |
| 외부 연동 또는 정합성 변경 | 계약과 실패 기준 검토, 통합 및 시나리오 검증 |
| 문서 또는 단순 설정 | 관련 빌드와 설정 확인 |

기존 테스트로 충분하면 중복 테스트를 추가하지 않습니다.
테스트를 실행할 수 없음과 구현 결함은 구분합니다.
컴파일 오류와 환경 문제를 기능 실패의 증거로 취급하지 않습니다.
테스트 통과만으로 요구사항 충족을 단정하지 않습니다.
요구사항 충족과 기존 동작의 회귀를 함께 봅니다.
통과를 위해 테스트를 삭제하거나 기대 결과를 약화하지 않습니다.

실행 가능한 테스트를 먼저 작성하는 작업에서는, 기대한 동작이 없을 때 실패하는지 확인합니다.
Spring의 배치와 명명은 [테스트 기본 구조](/docs/knowledge/backend/testing/test-structure)를 따릅니다.
자동화가 어려운 기준은 검증 방법과 필요한 증거를 적습니다.

## 기준에 적을 내용

| 기준 ID | 요구사항 | 초기 상태 또는 입력 | 행동 | 기대 결과 | 테스트 경계 | 검증 방법 |
|---|---|---|---|---|---|---|

기준이 잘못되면 근거와 함께 다시 정합니다.
기준을 바꾸면 이유, 영향, 관련 테스트를 함께 갱신합니다.
