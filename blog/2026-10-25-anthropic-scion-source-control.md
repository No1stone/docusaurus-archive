# Anthropic은 왜 Git을 버리고 Scion을 만들었을까?

*AI Agent 시대, 코드 작성보다 버전 관리가 병목이 된 이유*

2026년 10월, Anthropic은 흥미로운 기술적 결정을 공개했다.

자사의 핵심 모노레포를 Git에서 자체 개발한 버전 관리 시스템 **Scion**으로 완전히 이전했다는 것이다.

Git은 수십 년간 소프트웨어 개발의 표준으로 자리 잡은 도구다. 그런데 AI Coding Agent를 가장 적극적으로 활용하는 기업 중 하나인 Anthropic은 왜 새로운 버전 관리 시스템을 만들어야 했을까?

결론부터 말하면 Git이 잘못 설계되었기 때문은 아니다.

**코드를 생산하는 주체와 생산 속도가 달라지면서 기존 개발 인프라의 설계 전제가 맞지 않기 시작했기 때문이다.**

## 1. 코드 작성이 더 이상 병목이 아니었다

기존 소프트웨어 개발에서 가장 큰 제약 중 하나는 개발자가 코드를 작성하고 수정하는 데 필요한 시간이었다.

Git, 코드 리뷰, CI/CD 등은 이러한 인간 개발자의 작업 속도를 전제로 발전해 왔다.

하지만 Claude와 같은 AI Coding Agent가 코드 작성, 수정, 테스트를 반복하면서 상황이 달라졌다.

Anthropic이 공개한 수치는 상당히 인상적이다.

| 지표 | 규모 |
|---|---:|
| 2026년 5월 일일 병합 | 약 2,500건 |
| 2026년 9월 일일 병합 | 30,000건 이상 |
| 메인 브랜치 Git 이력 | 약 100GB |
| 압축된 작업 복사본 | 25GB 이상 |
| CI 코드 체크아웃 | 하루 약 2,500만 회 |
| 단순 Git 전송량 추정 | 하루 600PB 이상 |

불과 4개월 사이 일일 병합 건수가 12배 이상 증가했다.

이러한 환경에서는 코드 작성 자체보다 코드를 가져오고, 변경 이력을 계산하고, 병합하고, 테스트하는 인프라가 더 큰 제약이 된다.

Anthropic은 Git 미러 서버를 수백 대 운영하고 shallow clone, sparse checkout, 저장소 스냅샷 등의 최적화도 적용했다.

하지만 변경량이 계속 증가하면서 기존 방식을 유지하는 비용과 복잡성도 커졌다.

결국 문제는 단순히 Git 서버를 증설한다고 해결되는 수준을 넘어섰다.

## 2. Git의 장점이 오히려 부담이 된 이유

Git의 핵심 철학은 분산 버전 관리다.

개발자는 저장소를 복제한 뒤 네트워크 연결 없이도 커밋, 이력 조회, 차이 비교 등의 작업을 수행할 수 있다.

이것은 Git이 성공한 중요한 이유다.

하지만 Anthropic의 개발 환경에서는 다른 특성이 나타났다.

대부분의 클라이언트가 사람이 아니라 AI Agent, CI 작업, 자동화된 연구 프로세스였고, 이들은 기본적으로 네트워크에 연결된 상태에서 실행됐다.

이 환경에서는 모든 클라이언트가 독립적인 저장소 기능을 갖출 필요가 줄어든다.

예를 들어 CI 작업이 특정 커밋의 변경 파일 목록만 필요하다고 가정해 보자.

Git 기반 환경에서는 해당 정보를 계산하기 위해 저장소 데이터와 이력을 가져와야 할 수 있다.

반면 중앙 서버가 변경 이력을 직접 계산해 API로 제공한다면, 클라이언트는 결과만 받아도 된다.

**모든 작업 환경이 저장소를 소유할 필요는 없다는 것이다.**

Anthropic은 바로 이 전제를 바꾸었다.

## 3. Scion은 무엇이 다른가?

Scion은 대규모 모노레포와 항상 온라인 상태인 Agent를 전제로 설계한 중앙 서버 중심 버전 관리 시스템이다.

Git과 가장 큰 차이는 클라이언트와 서버의 역할이다.

| 구분 | Git | Scion |
|---|---|---|
| 기본 구조 | 분산형 | 중앙 서버 중심 |
| 커밋 생성 | 로컬 | 서버 |
| 병합 및 Rebase | 주로 로컬 | 서버 |
| 이력 조회 | 로컬 저장소 기반 | 서버 API |
| 데이터 보관 | 클라이언트도 저장 | 중앙 저장소와 계층형 캐시 |
| 체크아웃 | 로컬 파일 구성 | Sparse 및 가상화 중심 |
| 오프라인 작업 | 가능 | 서버 연결 전제 |

Scion에서는 커밋을 만들기 위해 로컬에서 완전한 저장소를 관리하고 Push하는 과정이 필요하지 않다.

변경 사항을 서버에 전달하면 서버가 Changeset을 생성한다.

또한 이력 조회, Blame, Diff, Merge Base 계산 등의 기능을 API로 제공한다.

따라서 Agent와 CI는 필요한 정보만 요청할 수 있다.

## 4. Scion의 핵심 설계

### Changeset 중심의 데이터 구조

Git의 커밋은 파일 트리 구조를 참조한다.

반면 Scion의 Changeset은 부모 Changeset을 기준으로 변경된 파일 목록과 해당 파일 콘텐츠의 주소를 저장한다.

이 Changeset은 Write-Ahead Log에 기록된다.

변경 이력과 파일별 Blame 등의 정보는 별도 파생 데이터(Derived Data)로 계산한다.

이 구조의 목적은 전체 저장소 크기와 관계없이 개별 변경 사항을 효율적으로 처리하는 것이다.

### 계층형 캐시 구조

Scion은 클라이언트가 필요한 파일 객체만 요청하도록 설계되어 있다.

주요 구성 요소는 다음과 같다.

- **scn:** 개발자와 작업 환경에서 사용하는 클라이언트
- **scion-daemon:** 동일 노드의 작업들이 공유하는 로컬 객체 캐시
- **scion-cache:** 리전 단위의 캐시 서버
- **scion-server:** 변경 이력과 객체를 제공하는 원본 서비스

각 계층은 변경되지 않는 콘텐츠 주소 기반 객체를 캐싱한다.

이 때문에 같은 파일을 여러 작업이 요청하더라도 매번 원본 저장소에서 가져올 필요가 없다.

Anthropic에 따르면 각 캐시 계층의 적중률은 99% 이상이다.

### 체크아웃 자체를 줄인다

Scion의 또 다른 특징은 체크아웃이 필수가 아니라는 것이다.

파일 변경 이력이나 Diff만 필요한 작업은 서버 API를 호출하면 된다.

실제 파일이 필요한 작업에서도 필요한 디렉터리나 파일만 가져오는 Sparse Checkout과 Virtualized Checkout을 활용한다.

결국 핵심은 **코드를 얼마나 빠르게 복제할 것인가가 아니라, 애초에 얼마나 적게 복제할 것인가**에 있다.

## 5. 실제로 어느 정도 개선되었을까?

Anthropic이 발표한 내부 운영 결과는 다음과 같다.

| 지표 | 발표된 개선 효과 |
|---|---|
| 소스 관리 인프라 CPU 및 메모리 규모 | 기존 Git 미러 대비 약 200배 축소 |
| CI 및 연구 작업 체크아웃 | 분 단위에서 초 단위로 개선 |
| CI CPU 용량 | 약 25% 절감 |
| 개발 및 전환 기간 | 약 5개월 |
| 핵심 개발 인력 | 7명 |

이 수치는 Anthropic의 대규모 모노레포와 내부 운영 환경에서 측정된 결과다. 일반적인 프로젝트에서도 동일한 개선 효과가 발생한다는 의미는 아니다.

그럼에도 상당히 흥미로운 사례다.

특히 Claude를 활용해 Scion 자체를 개발했다는 점이 눈에 띈다.

AI Agent가 기존 개발 인프라의 한계를 발생시켰고, 다시 AI Agent를 활용해 그 한계를 해결하는 시스템을 만든 것이다.

## 6. Git만 바꾼 것이 아니었다

Scion 도입은 버전 관리 도구 하나를 교체하는 작업으로 끝나지 않았다.

Anthropic은 코드 리뷰 도구인 Antique, 코드 검색, 접근 권한 관리, 병합 및 배포 프로세스까지 함께 구축했다.

여기서 또 다른 변화가 나타난다.

기존 CI/CD에서는 변경 사항을 병합하기 전에 테스트하고 검증하는 방식이 중요하다.

하지만 수백 또는 수천 건의 변경이 동시에 진행된다면 테스트가 실행되는 동안에도 메인 브랜치가 계속 바뀔 수 있다.

Anthropic은 이러한 환경에서 전역 병합 잠금에 의존하는 방식 대신 병합 이후와 배포 이전의 자동화된 검증을 강화하고 있다고 설명한다.

이는 테스트를 포기한다는 의미가 아니다.

**변경 사항이 지속적으로 발생하는 환경에 맞춰 검증 시점과 방식을 다시 설계한다는 의미다.**

## 7. Scion이 Git을 대체할 수 있을까?

현재로서는 일반적인 Git 대체재로 보기 어렵다.

Anthropic 역시 Scion이 범용적인 Git 대체 시스템에 적합하지 않다고 설명한다.

Scion은 거대한 모노레포와 대규모 Agent 작업이라는 특수한 환경을 해결하기 위해 만들어졌다.

중앙 서버에 대한 의존성도 높으며, 도입하려면 버전 관리뿐 아니라 코드 리뷰, 검색, CI 등의 개발 도구를 함께 재구성해야 한다.

또한 Git의 오프라인 작업과 분산형 구조는 여전히 많은 개발 환경에서 유용하다.

Scion의 설계에는 Google Piper와 Meta Sapling의 서버 구성 요소인 Mononoke 등 기존 대규모 소스 관리 시스템의 영향도 있다.

완전히 새로운 개념이 등장했다기보다는, 기존 대규모 소스 관리 기술을 AI Agent 환경에 맞춰 발전시킨 사례로 보는 편이 정확하다.

## 8. 이번 사례가 보여주는 변화

Scion에서 가장 흥미로운 부분은 새로운 버전 관리 시스템 자체보다 그것이 등장한 배경이다.

과거에는 개발자의 코드 작성 속도가 소프트웨어 생산량을 제한했다.

이제 AI Agent가 그 제약을 줄이면서 다른 문제가 드러나기 시작했다.

소스 관리, CI, 코드 리뷰, 테스트, 배포 등 개발 인프라 전체가 새로운 생산 속도를 감당해야 하는 상황이다.

이러한 변화는 단순히 개발 도구의 성능 개선만으로 해결되지 않을 수 있다.

기존 도구가 전제로 삼았던 작업 방식 자체를 다시 검토해야 할 수도 있다.

물론 모든 조직이 Anthropic과 같은 규모의 문제를 경험하는 것은 아니다. 대부분의 개발팀에서는 여전히 Git이 합리적인 선택이다.

그러나 Scion은 앞으로의 개발 인프라가 어떤 방향으로 발전할 수 있는지 보여주는 흥미로운 사례다.

**AI가 코드를 더 빠르게 작성하는 시대에는, 코드를 관리하는 시스템도 그 속도에 맞춰 변화해야 한다.**
