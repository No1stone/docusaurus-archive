# 공유 서버의 작은 게이트웨이, G1 GC로 시작한 이유

내 서버를 개발하면서 GC를 무엇으로 사용할지 고민했습니다. Java 25를 사용하니 Generational ZGC도 선택할 수 있지만, 이번에는 G1 GC로 시작하기로 했습니다.

판단의 출발점은 가장 짧은 GC 정지 시간이 아니었습니다. **이 서버가 다른 서비스와 같은 장비에서 실행된다는 점**이었습니다.

## 내 서버만 빨라서는 안 된다

내 서버의 주된 역할은 외부 API를 호출하고, 응답을 변환하고, 필요한 경우 재시도하는 것입니다. 경비실에서 카드를 등록하거나 조회하는 요청과 입출차 이벤트도 처리합니다.

이런 서버는 혼자 빨라지는 것만으로 전체 응답 시간이 줄어들지 않습니다. 호출 대상이 느려지면 그 응답을 기다려야 하기 때문입니다.

같은 장비의 CPU와 메모리를 과도하게 사용해 다른 서비스가 느려진다면, 결국 내 서버의 처리 시간에도 영향을 줍니다. 따라서 이번에는 내 서버의 정지 시간을 극도로 줄이는 것보다 **함께 실행되는 서비스가 사용할 자원 여유를 남기는 것**을 우선했습니다.

## 예상 요청량은 어느 정도일까

설치 장비의 메모리는 16GB이며 다른 서비스와 공유합니다. 요청 규모는 최대 1만 세대를 기준으로 잡았습니다.

| 항목 | 산정 기준 |
|---|---|
| 최대 세대 수 | 10,000세대 |
| 세대당 차량 수 | 1.5대 |
| 전체 차량 수 | 15,000대 |
| 일일 이벤트 산정 조건 | 모든 차량이 입차, 출차를 각각 1회 수행 |
| 일일 입출차 이벤트 | 30,000건 |
| 24시간 평균 | 초당 약 0.35건 |
| 집중 시간대 예상 | 초당 약 2건 |
| 여유를 둔 확인 기준 | 초당 5건 |
| 기타 요청 | 경비실의 카드 등록, 조회 등 간헐적인 요청 |

하루 3만 건이 많아 보일 수 있지만, 시간으로 나누면 요청률은 높지 않습니다. 다만 일평균만으로 출퇴근 시간대의 집중을 설명할 수는 없어 초당 5건도 확인 기준으로 잡았습니다.

이벤트 하나가 여러 외부 호출이나 DB 처리로 이어질 수 있으므로, 이벤트 수와 내부 작업 수는 구분해서 봅니다.

## Java 25에서 G1과 ZGC를 비교한 기준

G1과 Java 25의 ZGC는 모두 세대형 수집기입니다. 객체를 수명에 따라 나눠 처리한다는 점은 같지만, 수집 작업을 수행하는 방식과 목표는 다릅니다.

G1은 애플리케이션을 잠시 멈추는 작업을 일부 허용하면서 처리량과 정지 시간의 균형을 추구합니다. ZGC는 주요 작업을 애플리케이션과 동시에 수행해 정지 시간을 크게 줄입니다.

현재 서버에는 매우 짧은 GC 정지가 필수인 요구사항이 없습니다. 따라서 ZGC의 저지연 특성보다 G1의 균형을 먼저 검토했습니다.

| 서버의 조건 | 선택에 반영한 판단 |
|---|---|
| 초저지연이 필수가 아님 | 매우 짧은 GC 정지의 우선순위가 낮습니다. |
| 다른 서비스와 CPU 공유 | GC 정지 시간뿐 아니라 수집 작업의 CPU 사용량과 순간 피크가 중요합니다. |
| 다른 서비스와 메모리 공유 | 살아 있는 객체와 수집에 필요한 여유 공간을 포함해 실제 메모리 점유를 확인해야 합니다. |
| 외부 API 연동 중심 | 현재까지 GC 정지가 주요 병목이라는 근거는 없습니다. |

**G1이 항상 ZGC보다 CPU와 메모리를 적게 사용한다는 뜻은 아닙니다.** G1도 동시 작업과 병렬 수집을 수행하며, ZGC 역시 세대형으로 개선되면서 자원 효율이 좋아졌습니다.

이번 선택은 요구하지 않은 초저지연을 우선하기보다, G1을 기준으로 현재 업무에 필요한 자원을 확인하겠다는 판단입니다.

## 초기 힙은 작게, 최대 힙에는 여유를

힙은 다음과 같이 설정했습니다.

```groovy
def serverJvmArgs = [
        '-Xms64m',
        '-Xmx512m',
        '-XX:+UseG1GC',
]
```

| 옵션 | 의미 |
|---|---|
| `-Xms64m` | 초기 힙을 64MiB로 설정 |
| `-Xmx512m` | 힙이 필요에 따라 최대 512MiB까지 확장되도록 설정 |
| `-XX:+UseG1GC` | G1 GC 사용 |

최대 힙을 512MiB로 설정했다고 시작부터 전부 점유하는 것은 아닙니다. 평소에는 작게 시작하고, 요청 집중이나 외부 응답 지연으로 처리 중인 데이터가 늘어날 때 확장할 여유를 둔 것입니다.

또한 `-Xmx`는 JVM 전체 메모리의 상한이 아닙니다. 클래스 메타데이터, 스레드, 코드 캐시 등의 메모리는 별도로 사용합니다. 현재는 내 서버 프로세스 전체에 강제 메모리 제한을 설정하지 않습니다.

## 선택의 기준은 연동 전체의 응답

이번 서버에서는 GC 정지 시간을 얼마나 줄였는지보다, 주어진 요청을 처리하면서 주변 서비스에 어떤 영향을 주는지가 더 중요합니다.

G1으로 시작하되 CPU 사용량과 순간 피크, 메모리 점유, 외부 응답 지연 시 요청 적체를 함께 확인할 예정입니다. 요청량과 힙 사용량이 작은 환경에서는 Serial GC도 비교 대상으로 남겨두었습니다.

다른 서비스가 원활하게 응답할 수 있도록 자원 경쟁을 줄이는 것. 이번 서버의 GC를 선택하면서 가장 중요하게 본 기준입니다.
