# 커서 실사용 모델 선택방법

Cursor를 업데이트하면 가끔 모델 선택 화면이 초기화됩니다.
켜 두었던 것만 남는 게 아니라, 쓸 만한 최신이 한꺼번에 다시 켜진 상태가 됩니다.

{/* truncate */}

![Cursor IDE 모델 토글이 업데이트 후 대부분 켜진 화면](/img/blog/cursor-model-toggles-after-update.png)

처음에는 “또 설정을 맞춰야 하나” 싶었습니다.
지금은 덜 당황합니다.
제가 맞추고 싶은 것은 IDE에 켜 둔 스위치 목록이 아니라, **에이전트가 같은 지도를 보고 일하게 하는 쪽**이기 때문입니다.

이 글은 세 가지를 한곳에 모읍니다.
하네스에서 Master와 worker에 모델을 나누는 방식, 아카이브만 보면 잘 안 보이지만 실제로 그렇게 돌리는 실사용, ExampleItem 원셋으로 도메인과 변수만 바꿔 토큰을 줄이려는 희망입니다.

## 1. 지도는 고정하고, 모델만 갈아끼운다

제가 말하는 하네스는 회사나 프로젝트에 맞춰 튜닝하는 작업복에 가깝습니다.
자율 에이전트 제품을 새로 만드는 일과는 결이 다릅니다.
프로젝트를 아는 사람이 수정 포인트와 에러 포인트를 좁혀 두고, 그 위에서 모델 성능을 붙입니다.

그래서 모델 정책도 “제일 비싼 모델만 켠다”가 아닙니다.
역할마다 후보 풀을 두고, 제품에 있는 것부터 고릅니다.

| 역할 | 의도 | 대략의 풀 |
|------|------|-----------|
| Master | 라우팅, 공백 확인, 승인, 개발자와 대화 | Opus급. 없으면 강한 Sonnet으로 다운그레이드하고 알림 |
| Implementer, Reviewer, Tester, Scout, Curator 등 | 좁은 미션 실행 | Kimi code, Haiku, Composer-fast, Flash 같은 저렴한 코딩·체크 풀 |

아카이브의 [Agents Catalog](/docs/harness/agents/)에도 같은 원칙이 있습니다.
Master만 강한 풀을 쓰고, worker는 값싼 풀을 씁니다.
루틴 worker에 비싼 K3-max를 기본으로 두지 않습니다.
목록의 slug는 제품 UI가 자주 바뀌므로, 정확한 이름보다 **티어 의도**(Opus-class / Kimi-code / Haiku / Composer-fast)로 맞춥니다.

업데이트로 토글이 전부 켜져도, 하네스가 이미 “누가 무엇을 쓰는지”를 나눠 두었다면 IDE는 나중에 정리하면 됩니다.
평소에는 후보에 있는 값싼 worker를 고르고, 설계가 흔들릴 때만 강한 모델을 쓰면 됩니다.

중요한 것은 모델이 바뀌어도 **열 파일, 맞출 계층, 통과 기준**이 같이 바뀌지 않는 것입니다.
지도가 그 역할을 합니다.

## 2. 실사용은 아카이브 양만으로 증명되지 않는다

공개 아카이브만 돌리면 “문서를 많이 쓴 사람”으로 읽히기 쉽습니다.
실사용 증거는 잘 안 보입니다.
채용이나 외부 AI가 저장소만 보면 그렇게 나오는 것이 자연스럽습니다.

다만 제 쪽에서는 이 지도를 실제로 많이 돌립니다.
원셋을 복사하고, 규칙을 고치고, 에이전트와 함께 계층과 네이밍을 맞추고, 깨진 링크와 빌드까지 확인하는 일이 일상입니다.
모델 풀을 나누어 둔 것도 비용 이론이 아니라, worker를 값싼 모델로 돌리면서 Master가 결과를 다시 보게 하려는 운영입니다.

아카이브가 커도 목표는 전부를 읽히는 것이 아닙니다.
**확실한 입구와 원셋, 이번 작업에 필요한 문서만** 보게 하는 것이 목표입니다.
새 모델이 나오면 그 성능을 최대한 쓰되, 포인트를 잡는 개념은 지도에 남겨 둡니다.
모델 교체가 지도 교체가 되지 않게 하는 것이 실사용의 핵심입니다.

외부에 이를 보여 주려면 저장소 규모보다, 한 줄 설명과 짧은 사례가 더 잘 먹습니다.
예를 들면 이런 문장입니다.

> 원셋과 계층, 네이밍을 정규화해 두고, 사람과 AI가 같은 지도로 수정과 장애 지점을 좁힌다.
> 모델은 바뀌어도 지도는 유지하고 성능만 붙인다.
> 일상 구현은 저렴한 coding 풀, 라우팅과 승인은 강한 풀을 쓴다.

이 글이 그런 실사용 기록의 한 조각이기도 합니다.

## 3. 원셋은 도메인과 변수만 나오게 하기 위한다

백엔드 ExampleItem 원셋의 희망은 단순합니다.
계층, 메서드 골격, 테스트 뼈대는 이미 통과한 형태를 두고, **도메인 이름과 내부 필드, 경로, 테이블**만 바꿉니다.
그렇게 되면 단위 테스트와 시나리오가 같은 모양으로 돌아가고, AI에게 구조를 처음부터 발명하게 두지 않아도 됩니다.

프롬프트도 짧아집니다.
“이 원셋을 복사하고 토큰만 채워라”가 기본이 되면, 매 세션마다 아키텍처를 설득하는 토큰이 줄어듭니다.
값싼 worker 모델과도 잘 맞습니다.
지도와 템플릿이 있으면 모델이 약해도 손이 갈 자리가 분명하고, 모델이 강하면 같은 자리 위에서 더 잘 채웁니다.

물론 템플릿과 저장소가 어긋나거나, Item 확장, MSA처럼 원셋이 아직 얇은 구간에서는 설명이 다시 길어집니다.
정규화의 ROI는 “문서 장수”가 아니라 **복사가 실제로 돌아가는지**에서 납니다.

프론트와 Flutter도 같은 언어로 맞추는 중이고, MSA는 유스케이스성이 커서 천천히 계약과 통신 패턴 쪽으로 정규화를 올리면 됩니다.
백과 DB 쪽 원셋, 계층, 공통코드, DTO 사다리가 먼저 앉은 이유도 여기에 있습니다.

## 정리

Cursor 모델 목록이 초기화돼도, 제가 붙잡고 싶은 것은 스위치 전체가 아닙니다.

1. **모델 풀** — Master는 강하게, worker는 저렴하게. slug보다 티어 의도.
2. **실사용** — 큰 아카이브의 목적은 지도다. 새 모델은 성능만 교체한다.
3. **원셋** — 구조는 고정하고 도메인과 변수만 바꾼다. 토큰과 재작업을 같이 줄인다.

랩이 만드는 범용 자율 런타임과, 회사 프로젝트에 맞춘 하네스는 고객이 다릅니다.
저는 후자 쪽 유저로, 지도를 작성하고 실제로 돌리며 다듬고 있습니다.
모델은 자주 바뀝니다.
그래도 수정 포인트를 찾는 방식만큼은 쉽게 바뀌지 않게 두는 것이, 제가 AI 시대에 엔지니어로 남고 싶은 방식입니다.
