# AI 바이브 코딩과 하네스에는 어떤 방식이 있을까?

AI와 개발하는 방식은 다양합니다.  
대화로 기능을 하나씩 만들어 가기도 하고, 구현과 검증 절차를 하네스에 정해 두고 결과가 기준을 만족할 때까지 반복하기도 합니다.  
MCP로 이슈 트래커나 외부 도구를 연결해 작업에 필요한 정보를 가져올 수도 있습니다.

방식을 살펴보다 보면 비슷한 질문이 반복됩니다.  
무엇을 먼저 정의할까요?  
AI에게 어느 순서로 일을 맡기고, 어디까지 판단하게 할까요?  
어떤 파일과 도구를 사용할 수 있게 하고, 무엇을 확인했을 때 작업을 끝낼까요?

개발 방식에 붙는 이름은 이런 질문 중 **무엇을 기준으로 삼는지**를 보여줍니다.

{/* truncate */}

| 기준 | 답하는 질문 | 개발 과정에서 하는 일 |
|---|---|---|
| **Specification-Driven Development (SDD)** | 제품은 어떻게 동작해야 할까? | 명세에 요구사항과 예외 조건을 정하고 구현과 검증의 기준으로 삼습니다. |
| **Template-Driven Development** | 어떤 구조에서 구현을 시작할까? | 검증된 코드와 테스트를 묶은 원셋을 가져와 이번 기능에 필요한 부분을 채웁니다. |
| **Test-Driven Development (TDD)** | 어떤 동작을 먼저 검증할까? | 실패하는 테스트로 기대 동작을 표현하고, 테스트를 통과시키며 구현을 다듬습니다. |
| **Context-Driven Development** | AI가 작업 전에 무엇을 알아야 할까? | 이번 작업과 관련된 명세, 코드, 설계 결정, 작업 기록을 연결합니다. |
| **Eval-Driven Development** | AI가 같은 종류의 작업을 얼마나 일관되게 수행할까? | 반복 가능한 과제와 평가 기준을 두고 모델이나 하네스를 바꿨을 때 결과를 비교합니다. |
| **Single Source of Truth (SSOT)** | 내용이 엇갈리면 어디를 기준으로 볼까? | 정보별 정본과 참조 링크를 관리합니다. 예를 들어 Jira 티켓, ADR, 제품 명세, 개발 히스토리가 각각 다른 정보를 맡을 수 있습니다. |

한 프로젝트에서도 이 기준들은 함께 쓰입니다.  
제 하네스는 원셋을 구현의 출발점으로 삼습니다.  
제품 명세에서 기대 동작을 확인하고, 원셋에서 코드 구조와 테스트를 가져온 뒤, 이번 기능에서 달라지는 부분을 채웁니다.  
루프는 구현과 검증을 반복하는 순서를 다루고, MCP는 그 과정에서 필요한 정보와 도구를 연결합니다.

### 하네스를 설계하다 보면 다시 개발 관리로 돌아옵니다

AI에게 테스트를 반복하게 하는 건 비교적 구체적인 지시입니다.  
그런데 테스트를 통과시키려면 기존 API 응답을 바꿔야 한다는 결론이 나오면 어떻게 할까요?  
이번 작업에서 계약 변경까지 허용하는지, 그 결정을 누가 내리는지, 결정이 바뀌면 어느 문서를 갱신해야 하는지부터 정해야 합니다.

이 지점에서 하네스 설계는 프로젝트 관리와 아키텍처 관리의 질문으로 이어집니다.  
**작업 범위를 누가 정하고, 계층과 모듈의 경계를 어디에서 확인하고, 변경이 끝났다는 판단을 누가 어떤 근거로 내리는가** 하는 질문입니다.  
작업 범위는 Jira 티켓에, 유지할 동작은 명세에, 오래 남을 설계 판단은 ADR에, 실제 변경과 검증 결과는 개발 히스토리에 남길 수 있습니다.

제 하네스에서는 AI가 정해진 범위 안에서 구현하고 검증합니다.  
기존 계약을 바꾸거나 새 의존성을 도입해야 한다면, 그 영향과 선택지를 정리해 개발자가 결정할 수 있게 합니다.  
이렇게 역할과 기록의 위치를 정해 두면 다음 개발자나 AI도 같은 근거를 읽고 작업을 이어갈 수 있습니다.
