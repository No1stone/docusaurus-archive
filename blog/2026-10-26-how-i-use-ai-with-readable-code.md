# 내가 AI를 쓰는 법 — 코드는 맡기고, 읽는 기준은 유지하기

AI를 사용하면서 구현 속도는 빨라졌습니다. 하지만 생성된 코드가 늘어날수록 다른 고민이 생겼습니다.

<!-- truncate -->

같은 기능을 요청해도 파일 배치와 메서드 구성이 달라집니다. 간단한 질문을 했는데 문서까지 수정하기도 하고, 작은 변경에 여러 검토 절차가 붙기도 합니다.

그래서 제가 원하는 것은 단순히 코드를 많이 만드는 AI가 아닙니다.

**제가 익숙하게 읽을 수 있는 구조로 구현하고, 필요한 검증을 수행하는 AI**입니다.

## 코드 컨벤션을 유지하려는 이유

저는 코드 컨벤션과 템플릿으로 계층별 책임, 파일 위치, DTO 형태와 메서드 구성을 맞춥니다.

이 기준이 있으면 코드를 확인할 때 어디를 봐야 할지 예상할 수 있습니다.

```text
요청 처리       → Controller
업무 흐름 조합  → Facade
데이터 접근     → Service·Repository
외부 통신       → Port·구현체
```

AI가 생성한 모든 코드를 매번 처음부터 정독하기는 어렵습니다. 대신 익숙한 구조를 유지하면 예상과 다른 의존성이나 로직의 위치를 더 빨리 발견할 수 있습니다.

물론 모양이 익숙하다고 동작까지 맞는 것은 아닙니다. 컨벤션은 검토를 쉽게 만들고, 테스트는 동작을 확인하는 역할을 합니다.

## 하네스에 너무 많은 것을 맡겨보기도 했다

처음에는 역할과 절차를 자세하게 정하면 더 안정적으로 개발할 수 있을 것으로 생각했습니다.

요구사항 분석, 구현, 리뷰, 테스트, 기록까지 흐름을 정했습니다. 실제로 도움이 되는 부분도 있었지만, 작은 작업에도 같은 절차가 적용되면서 부담이 생겼습니다.

“패키지순으로 알려줘”라고 했는데 README와 다이어그램까지 수정하는 식입니다.

문제는 역할의 존재보다 **언제 그 역할과 절차를 사용할지**였습니다.

지금은 결과물의 기준과 작업 방식을 나눠 생각합니다.

| 유지하는 기준 | 작업에 따라 맡기는 부분 |
|---|---|
| 코드 스타일과 계층 경계 | 탐색 순서와 구현 방법 |
| 기존 인터페이스와 템플릿 | 필요한 도구 선택 |
| 요구사항과 통과 기준 | 범위 안의 일상적인 판단 |
| 변경 범위와 검증 결과 | 역할 분리 여부 |

모델이 발전하면 과거에 필요했던 상세 지시가 오히려 방해가 될 수도 있습니다. 그래서 새로운 규칙을 추가하는 것만큼, 필요 없어진 절차를 걷어내는 것도 중요하게 보고 있습니다.

## 에이전트 역할은 책임을 나누는 기준이다

하네스에는 다음 역할을 정의해 두었습니다.

| 역할 | 책임 |
|---|---|
| **Master** | 요구사항과 범위를 정리하고, 통과 기준과 완료 여부 판단 |
| **Scout** | 기존 구조와 구현을 탐색하고 관련 코드·문서 위치 파악 |
| **Tester** | 정상·경계·실패 테스트 작성과 실행 |
| **Reviewer** | 요구사항과 설계 원칙에 맞는지 검토 |
| **Implementer** | 기존 코드와 템플릿을 활용해 구현 |
| **QA** | 사용자 관점의 요구사항 충족과 회귀 확인 |

역할이 여섯 개라고 매번 에이전트 여섯 개를 실행하는 것은 아닙니다.

작은 작업은 하나의 에이전트가 구현과 검증을 함께 수행합니다. 작업이 크거나 별도의 검토가 필요할 때만 역할을 분리합니다.

역할표는 조직도를 흉내 내기 위한 것이 아니라, 작업에서 빠뜨리면 안 되는 책임을 확인하기 위한 기준입니다.

## 두 종류의 세션을 나눠 쓴다

현재는 하네스 적용 세션과 가벼운 일반 세션을 구분해 사용합니다.

![Cursor에서 partner-gateway 저장소 아래 하네스 적용 세션과 가벼운 일반 세션을 나눈 모습](/img/blog/cursor-harness-and-light-sessions.png)

| 세션 | 주로 하는 작업 | 운영 방식 |
|---|---|---|
| **하네스 적용** | 기능 개발·구조 변경·테스트 | 필요한 규칙·템플릿·검증 절차 참조 |
| **일반 세션** | 간단한 질문·코드 확인·소규모 수정 | 필요한 코드와 지시만 전달 |

두 세션을 나누는 이유는 토큰 사용량 때문입니다. 간단한 질문에 프로젝트 지식과 작업 절차를 매번 불러올 필요는 없다고 생각했습니다.

일반 세션이라고 품질 기준을 없애는 것은 아닙니다. 기존 코드 스타일을 따르고, 동작을 바꿨다면 필요한 확인은 합니다. 줄이려는 것은 불필요한 컨텍스트와 절차입니다.

제가 구성한 환경에서는 세션을 시작할 때 의도를 명시합니다.

하네스를 사용할 때는 다음과 같이 시작합니다.

```text
하네스 적용해 줘.
```

가벼운 작업용 세션에서는 이렇게 안내합니다.

```text
이 세션은 간단한 질문, 코드 확인, 소규모 수정에 사용할 거야.
하네스 문서를 별도로 로딩하지 말고,
필요한 코드와 기존 규칙을 기준으로 간단하게 진행해 줘.
```

이 문구는 제가 정한 운영 방식입니다. 세션 이름만으로 적용 상태를 판단하지 않고, 실제로 어떤 규칙을 참조했는지와 작업 결과를 확인합니다.

## 구현은 맡겨도 완료 기준은 먼저 정한다

기능을 맡길 때는 무엇이 되면 완료인지부터 정리합니다.

```text
요구사항·범위 확인
    → 통과 기준 정의
    → 기존 코드·템플릿으로 구현
    → 필요한 테스트
    → 결과 검토
```

모든 변경에서 테스트 코드를 먼저 작성하도록 강제하지는 않습니다. 기존 테스트가 요구사항을 충분히 확인한다면 재사용합니다.

단위·통합·시나리오·E2E 중에서도 변경된 동작과 계약에 맞는 검증을 선택합니다. 토큰을 절약한다는 이유로 필요한 테스트를 빼거나, 실패한 테스트의 기대값을 낮춰 통과시키지는 않습니다.

질문과 구현 요청도 구분합니다. “확인해 줘”는 필요한 코드를 읽고 답하는 작업입니다. “고쳐줘”는 해당 범위를 수정하는 작업입니다. 이 차이만 명확히 해도 불필요한 파일 변경이 줄어듭니다.

## 모델은 바뀌어도 내 코드는 읽을 수 있어야 한다

코드 구현에는 Claude나 Cursor를 사용하고, 설계와 결과 검토에는 Codex와 Claude를 함께 활용합니다. 특정 도구 하나에 모든 역할을 고정하지는 않습니다.

모델이 바뀌어도 남기고 싶은 것은 같습니다.

기존 템플릿을 활용한 구조, 계층별 책임, 검증 가능한 결과, 다음 작업에 필요한 기록입니다.

작업 기록도 모든 대화를 남기는 대신 결정 사항과 변경 내용, 검증 결과와 미해결 항목만 유지하려고 합니다.

제가 AI를 쓰는 목적은 작업 과정을 세세하게 통제하는 데 있지 않습니다.

**문제 해결은 AI에게 맡기되, 결과물은 제가 익숙하게 읽고 빠르게 검토할 수 있는 코드로 남기는 것.** 지금 하네스를 다듬는 기준도 여기에 두고 있습니다.
