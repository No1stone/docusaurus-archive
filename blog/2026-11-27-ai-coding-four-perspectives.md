AI를 사용하면서 코드를 만드는 비용이 낮아졌다는 사실을 체감하고 있습니다.

예전에는 직접 작성하고 확인하는 데 며칠이 걸렸을 기능을 이제는 대화 몇 번으로 구현하기도 합니다.
익숙하지 않은 기술도 동작하는 예제를 먼저 만들어 보고, 코드를 읽으며 이해하는 순서로 접근할 수 있습니다.

그런데 만드는 속도가 빨라질수록 다른 질문도 생깁니다.

내가 충분히 이해하지 못하는 코드를 어디까지 운영해도 될까요?
AI가 추천한 설계는 어떤 기준으로 받아들여야 할까요?
구현 비용이 낮아진 만큼 보안, 유지보수와 운영 비용도 함께 낮아지고 있을까요?

{/* truncate */}

최근 개발자들의 AI 코딩에 대한 입장을 네 가지로 묶은 [「Programming Legends Are at War Over AI」](https://www.youtube.com/watch?v=HYNzbxII8oQ)를 보았습니다.
서로 다른 주장처럼 보였지만, 저는 어느 한쪽만 선택하기 어려웠습니다.
네 가지 생각이 제 안에도 함께 있었기 때문입니다.

아래 분류는 영상의 구성을 참고한 것입니다.
당사자들이 선언한 공식 학파는 아니며, 관점별 질문과 설명에는 제 해석을 덧붙였습니다.

## 같은 도구를 보면서 다른 질문을 한다

| 관점 | 영상에서 묶은 대표 인물 | 제가 받아들인 질문 |
|---|---|---|
| 회의적 관점 | 조지 호츠, 조너선 블로, 비야네 스트롭스트룹 | 생성된 결과를 사람이 이해하고 신뢰할 수 있는가? |
| 적극 수용 관점 | 안드레이 카파시, DHH, 스티브 예기 | 달라진 도구를 충분히 활용하고 있는가? |
| 실용적 관점 | 리누스 토르발스 | 실제로 쓸 만한 결과를 만드는가? |
| 규율과 설계 관점 | 켄트 벡, 로버트 C. 마틴 | 구현 방식이 바뀌어도 지켜야 할 개발 원칙은 무엇인가? |

회의적인 시선은 AI가 코드를 생성할 수 있다는 사실보다 그 결과를 얼마나 이해하고 검증할 수 있는지에 주목합니다.
적극 수용하는 시선은 도구가 이미 바뀌었는데 예전 작업 방식만 고집하고 있는 것은 아닌지 묻습니다.

실용적인 시선에서는 사람이 작성했는지 AI가 작성했는지보다 결과가 중요해집니다.
규율과 설계를 중시하는 시선에서는 생성 속도가 빨라져도 테스트와 변경 관리가 여전히 필요합니다.

켄트 벡도 자신의 작업을 소개하면서 AI와 협업하는 방식을 ‘Augmented Coding’으로 다루고 있습니다.
오랫동안 개발 원칙을 이야기한 사람이 AI를 거부하는 대신, 무엇이 달라지고 무엇이 남는지 실험하고 있다는 점이 흥미롭습니다.
[켄트 벡 공식 사이트](https://kentbeck.com/)에서 관련 작업을 소개하고 있습니다.

저는 이 관점들이 서로 완전히 배타적이라고 생각하지 않습니다.
도구를 적극적으로 사용하면서 결과를 의심할 수 있고, 가능성을 실험하면서 실제 비용을 따질 수도 있습니다.

## 저는 네 가지 생각을 함께 가지고 있습니다

저도 AI에 구현을 많이 맡깁니다.

반복적인 코드를 작성하고, 테스트를 보강하고, 새로운 기능의 골격을 만드는 데 AI가 주는 이점은 큽니다.
예전이라면 시간을 이유로 미뤘을 작업도 일단 시도해 볼 수 있습니다.

동시에 결과를 그대로 받아들이기는 어렵습니다.

동작하는 화면 뒤에서 어떤 쿼리가 실행되는지, 트랜잭션은 어디서 시작하고 끝나는지, 외부 호출이 실패하면 어떤 상태가 남는지는 확인하고 싶습니다.
기능이 완성됐다는 설명과 제가 운영할 수 있다고 판단하는 시점 사이에는 간격이 있습니다.

| 제가 가진 생각 | 실제 작업에서 하는 판단 |
|---|---|
| 구현은 적극 맡기고 싶습니다. | 반복 작업과 초안 작성은 AI를 활용합니다. |
| 이해하지 못하는 결과는 불안합니다. | 책임 경계와 데이터 흐름을 확인합니다. |
| 새로운 기술이 항상 이득은 아닙니다. | 기존 생태계와 운영 경험까지 비교합니다. |
| 일정한 개발 기준이 필요합니다. | 명세, 템플릿과 테스트로 판단 근거를 남깁니다. |

AI를 사용하지 않는 것만이 신중한 태도는 아닐 것입니다.
반대로 AI가 만든 결과를 바로 받아들이는 것만이 변화를 수용하는 태도도 아닐 것입니다.

저에게는 어디까지 맡기고, 무엇을 확인하며, 어떤 근거로 결정할지가 더 중요한 질문입니다.

## 코드를 만들었다는 것과 운영할 준비가 됐다는 것

이 차이를 보여주는 해외 사례도 있습니다.

Reddit의 시스템 관리자 커뮤니티에는 직원들이 직접 만든 앱을 배포해 달라고 요청하는 상황을 다룬 글이 올라왔습니다.
작성자는 직원용 대시보드를 만들었다며 특정 Python 버전과 SDK 설치, 회사 재무 파일에 대한 접근 권한을 요청하는 일이 늘었다고 설명합니다.
[원문: Vibe-coded app deployment requests from end users](https://www.reddit.com/r/sysadmin/comments/1tjochk/vibecoded_app_deployment_requests_from_end_users/)

개인의 경험담이므로 모든 조직의 상황으로 일반화할 수는 없습니다.
비개발자가 프로그램을 만들었다는 사실 자체가 문제라고 생각하지도 않습니다.
현업 담당자가 자신의 문제를 직접 해결할 수 있게 된 것은 분명한 변화입니다.

다만 제작자에게는 완성된 프로그램이, 운영 담당자에게는 이제 검토를 시작해야 하는 시스템일 수 있습니다.

| 제작자가 확인한 것 | 조직에서 추가로 확인할 것 |
|---|---|
| 원하는 화면이 나옵니다. | 누가 접근하고 어떤 권한을 갖습니까? |
| 데이터를 저장할 수 있습니다. | 어디에 저장하며 백업과 삭제는 어떻게 합니까? |
| 제 환경에서는 실행됩니다. | 배포와 롤백, 설정 변경은 어떻게 합니까? |
| 업무 시간을 줄여줍니다. | 유지 비용과 장애 대응 부담까지 감당할 만합니까? |
| 제가 만들었습니다. | 담당자가 바뀌거나 퇴사한 뒤에는 누가 관리합니까? |

저는 이런 사례가 앞으로 더 늘어날 것 같습니다.
프로그램을 만드는 문턱이 낮아진 만큼, 정식 개발 조직을 거치지 않고 업무 도구를 만드는 사람도 늘어날 수 있기 때문입니다.

처음에는 혼자 쓰던 도구라도 동료와 공유하고 다른 업무에서 결과를 사용하기 시작하면, 어느 순간 조직이 의존하는 시스템이 됩니다.
보안과 운영 검토는 그 뒤에 시작될 수도 있습니다.

그렇다면 만드는 사람이 절약한 시간이 운영팀과 보안팀의 검토 부담으로 옮겨가는 것은 아닌지도 살펴봐야 합니다.

## 작은 프로그램이 쌓이면 조직의 시스템이 된다

한 사람이 만든 작은 도구는 처음에는 부담이 작아 보입니다.
하지만 여러 부서에서 비슷한 도구를 만들기 시작하면 이야기가 달라집니다.

누가 언제 만들었는지 모르는 서버가 생깁니다.
개인 계정으로 만든 데이터베이스에 회사 자료가 저장될 수도 있습니다.
다른 팀이 그 프로그램의 결과를 사용하면서, 어느 순간 중단하기 어려운 의존성이 생길 수도 있습니다.

그때는 서버 목록을 찾는 것만으로 해결되지 않습니다.

무슨 데이터를 다루는지 알아야 합니다.
누가 사용하는지 찾아야 합니다.
없애도 되는지, 없애면 어떤 업무가 멈추는지 확인해야 합니다.
제작자와 사용자, 보안 담당자와 운영 담당자가 서로 설명하고 책임을 조정해야 합니다.

이 과정 자체가 비용입니다.

문서를 자동으로 생성할 수 있어도 그 문서가 현재 시스템과 맞는지 확인해야 합니다.
유지보수 담당자를 적어둘 수 있어도 그 사람이 실제로 시간과 권한을 갖고 있는지는 별개의 문제입니다.

코드를 빠르게 만드는 능력이 조직 전체의 관리 능력을 같은 속도로 늘려주지는 않습니다.

## 이미 운영 중인 시스템에서도 판단은 계속된다

이 문제는 새로운 시스템을 하나 들여올 때만 생기지 않습니다.
이미 크게 운영 중인 시스템에 기능 하나를 추가할 때도 같은 질문이 따라옵니다.

예를 들어 새로운 요구사항을 받았다고 해보겠습니다.
AI는 엔티티와 테이블, API와 화면을 빠르게 만들어줄 수 있습니다.
하지만 테이블을 추가하는 것이 맞는지부터 판단해야 합니다.

기존 모델로 표현할 수 있는 요구인지, 별도의 데이터 생명주기가 필요한지, 조회 편의를 위해 데이터를 중복 저장할지 검토해야 합니다.
새 테이블이 생기면 데이터를 채우는 방법뿐 아니라 동기화하고 정리하는 방법도 필요합니다.

| 결정할 것 | 함께 확인할 내용 |
|---|---|
| 테이블 추가 또는 기존 모델 확장 | 업무 책임, 데이터 중복, 조회와 변경 방식 |
| 마이그레이션 전략 | 기존 데이터 이관, 배포 순서, 구버전과의 호환성 |
| 데이터 관리 전략 | 정합성 기준, 재처리, 백업과 복구 |
| 보관 기간 | 업무 목적, 정책과 법적 요구, 아카이빙과 삭제 |
| 기술 선택 | 해결할 문제, 기존 구성과의 호환성, 운영 경험과 비용 |

마이그레이션 스크립트가 실행된다는 것만으로 배포 전략이 완성되는 것은 아닙니다.
데이터가 많은 환경에서 얼마나 오래 걸리는지, 락이 어떤 영향을 주는지, 작업 중 실패하면 어디서 다시 시작할지 알아야 합니다.

애플리케이션 버전만 되돌릴 수 있어도 이미 변경한 데이터까지 되돌릴 수 있는 것은 아닙니다.
컬럼을 추가하고 데이터를 이관한 뒤 기존 컬럼을 제거하는 순서에는, 코드 생성과 별개로 검토할 운영 조건이 있습니다.

이런 판단은 기능 하나를 구현할 때마다 크고 작은 형태로 반복됩니다.

## AI가 추천했기 때문에 선택해도 될까

AI는 기술 선택의 이유도 잘 설명합니다.

확장성, 성능, 유지보수성, 생산성과 같은 표현을 붙여 그럴듯한 비교표를 만들어줍니다.
하지만 일반적으로 타당한 설명이 지금 제 시스템에서도 타당한 결정인지는 따로 확인해야 합니다.

지금 필요한 처리량이 어느 정도인지.
팀이 그 기술을 운영해 본 적이 있는지.
기존 시스템과 연결하면서 무엇을 추가로 관리해야 하는지.
다른 방법보다 복잡해지는 만큼 얻는 이득이 있는지.

AI가 추천했다는 사실은 검토의 출발점이 될 수 있습니다.
선택의 이유를 대신할 수 있는지는 다른 문제입니다.

질문에 필요한 조건을 빠뜨렸다면 답변도 그 조건을 반영하지 못할 수 있습니다.
추천된 구성이 훌륭해 보여도, 제가 제공하지 않은 현장의 제약까지 알아서 맞춰줬다고 기대하기는 어렵습니다.

음악을 만드는 일과도 비슷하다고 생각합니다.

같은 도구로 곡을 만들더라도 음악을 아는 사람이 선택하고 다듬는 과정과, 나온 결과를 구분하기 어려운 사람이 받아들이는 과정은 다를 것입니다.
개발에서도 동작하는 결과를 얻는 것과, 왜 이 구조와 기술을 선택했는지 이해하는 것은 같지 않습니다.

그렇다고 모든 코드를 사람이 직접 작성해야 한다는 뜻은 아닙니다.
모든 라이브러리의 내부를 끝까지 알아야 한다는 뜻도 아닙니다.

중요한 것은 내가 맡은 범위에서 선택의 이유와 영향을 설명할 수 있는가입니다.
무엇을 확인했고 무엇은 아직 확인하지 못했는지 구분하고, 결과가 예상과 다를 때 다시 판단할 수 있어야 한다고 생각합니다.

## 하네스도 모든 것을 해결하지는 못한다

저는 일정한 구조와 구현 예제를 제공하는 하네스를 만들고 사용합니다.
AI가 매번 다른 구조를 만들지 않도록 원셋을 두고, 변경할 동작과 검증 기준을 정리합니다.

이런 준비는 반복 설명을 줄이고 결과를 검토하는 데 도움이 됩니다.
하지만 하네스를 잘 사용했다는 이유만으로 운영 준비까지 끝났다고 볼 수는 없습니다.

| 하네스로 도울 수 있는 부분 | 별도로 판단하고 합의할 부분 |
|---|---|
| 코드 구조와 구현 규칙 | 이 시스템을 도입하거나 변경할 업무상 가치 |
| 테스트 작성과 실행 절차 | 감수할 수 있는 장애와 데이터 손실 범위 |
| 문서와 변경 이력 관리 | 유지보수 담당자의 시간과 책임 |
| 배포 절차와 보안 검사 | 접근 승인, 운영 정책과 지속적인 비용 |

앞의 Reddit 사례에서 어떤 하네스를 사용했는지는 확인하지 않았습니다.
다만 유사한 문제가 하네스를 사용하지 않아서만 발생한다고 생각하지는 않습니다.

구현 규칙을 잘 지킨 프로그램도 운영 비용이 기대 효과보다 클 수 있습니다.
보안 검사를 통과한 프로그램도 조직이 장기간 관리할 이유가 없을 수 있습니다.
테스트를 통과한 변경도 실제 데이터와 배포 조건에서는 추가 검토가 필요할 수 있습니다.

제 하네스 역시 이런 판단을 돕는 수단입니다.
좋은 규칙을 넣어두면 모든 상황에서 좋은 결론이 나온다고 생각하지는 않습니다.
규칙이 현재 상황에 맞는지 확인하고 바꾸는 일도 결국 남습니다.

## 개발자라는 직업은 사라질까

코드 작성에 필요한 시간이 줄어든다면, 같은 일을 수행하는 데 필요한 인력도 줄어들 수 있습니다.
운영과 설계가 중요하다는 이유만으로 기존 일자리가 그대로 유지된다고 말할 수는 없습니다.

반대로 더 많은 사람이 프로그램을 만들게 되면 검토하고 연결하고 유지해야 할 시스템도 늘어날 수 있습니다.
하지만 늘어난 일이 줄어든 일자리를 같은 규모로 채워줄지도 알 수 없습니다.

그래서 저는 **‘개발자는 사라진다’는 결론을 쉽게 내리고 싶지 않습니다.**
코드를 만드는 비용이 낮아졌다는 사실만으로, 소프트웨어를 이해하고 검증하며 운영하는 데 필요한 역할까지 사라졌다고 보기는 어렵기 때문입니다.

지금 제가 궁금한 것은 비용이 어디로 이동하는가입니다.

구현 시간이 줄어든 만큼 요구를 설명하고 결과를 검토하는 시간이 늘어나는지.
개인이 절약한 시간이 다른 부서의 검토와 운영 부담으로 옮겨가는지.
AI가 그 과정까지 도우면 조직 전체의 비용도 실제로 줄어드는지.

비교해야 할 것은 코드 몇 줄을 만드는 가격만이 아닐 것입니다.
하나의 시스템을 도입하고, 사용하고, 바꾸고, 마지막에 없애는 동안 들어가는 비용도 함께 봐야 합니다.

저는 AI에 더 많은 일을 맡겨보고 싶습니다.
동시에 제가 이해하고 고칠 수 있는 범위를 유지하고 싶습니다.

새로운 가능성을 받아들이면서도 결과를 의심하고, 실제 효과를 따지면서 검증할 기준을 만드는 것.
지금은 그 네 가지 생각을 함께 가지고 개발하고 있습니다.
