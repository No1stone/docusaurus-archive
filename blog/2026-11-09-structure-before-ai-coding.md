# AI에게 코드를 맡기기 전에, 나는 구조부터 만들었다

### 바이브코딩의 오버엔지니어링을 경험하고 템플릿 기반 하네스를 구축하기까지

AI를 활용한 개발이 보편화되면서 코드를 작성하는 방식도 빠르게 변화하고 있다.

자연어로 요구사항을 설명하면 AI가 코드를 작성하고, 테스트를 만들고, 때로는 시스템 구조까지 설계한다.

나 역시 AI를 개발에 적극적으로 활용하고 있다.

처음에는 요구사항을 설명하고 구현을 맡기는 방식으로 접근했다. AI는 생각보다 코드를 잘 작성했고, 복잡한 기능도 빠르게 구현했다.

그런데 프로젝트가 커지고 기능이 늘어날수록 한 가지 문제가 눈에 들어오기 시작했다.

**코드는 잘 작성하는데, 그 코드가 위치하는 구조는 항상 적절하지 않았다.**

단순한 기능을 구현하는 데 불필요한 추상화가 추가되기도 했고, 기존 프레임워크가 제공하는 기능을 별도로 구현하기도 했다.

같은 성격의 기능인데도 구현할 때마다 서로 다른 패턴이 등장했다.

AI에게 원하는 방향을 다시 설명하면 수정은 가능했다. 하지만 그 과정에서 다른 계층에 새로운 복잡성이 생기거나, 기존 구조와 맞지 않는 구현이 추가되기도 했다.

그때부터 고민하기 시작했다.

**AI에게 더 상세한 프롬프트를 제공하는 것이 근본적인 해결책일까?**

내가 내린 결론은 조금 달랐다.

AI가 코드를 잘 작성하도록 만드는 것보다, AI가 좋은 구조 안에서 코드를 작성할 수 있도록 개발 환경을 먼저 설계하는 것이 중요하다고 생각했다.

이것이 내가 템플릿 기반 하네스 엔지니어링(Harness Engineering)을 구축하게 된 출발점이다.

## 1. AI는 코드를 잘 작성한다. 하지만 좋은 구조를 항상 선택하지는 않는다

AI의 코드 생성 능력은 이미 상당한 수준에 도달했다고 생각한다.

문제는 코드를 작성할 수 있느냐가 아니다.

**그 코드가 시스템 전체에서 어떤 책임을 가져야 하고, 어디에 위치해야 하는지를 판단하는 문제다.**

예를 들어 Spring Security를 생각해 보자.

Spring Security에는 인증과 인가를 처리하기 위한 다양한 기능이 이미 존재한다.

- `SecurityFilterChain`
- `AuthenticationProvider`
- `SecurityContextHolder`
- `UserDetailsService`
- `AuthenticationEntryPoint`
- `AccessDeniedHandler`

이러한 기능을 적절히 활용하면 인증된 사용자 정보, 권한 정책, 인증 실패 처리 등을 일관된 구조 안에서 관리할 수 있다.

하지만 AI에게 단순히 인증과 감사 로그를 구현해 달라고 요청하면 어떨까?

요구사항과 기존 구조에 따라 별도의 필터를 만들거나, 사용자 정보를 전달하기 위한 객체를 추가하거나, 이미 존재하는 기능을 다시 구현할 수도 있다.

물론 이런 구현이 반드시 잘못된 것은 아니다.

특정 요구사항에서는 커스텀 필터가 필요할 수 있고, 프레임워크의 기본 기능만으로 해결하기 어려운 문제도 존재한다.

중요한 것은 **그 구현이 정말 필요한가를 판단할 수 있어야 한다는 점**이다.

단순히 코드가 동작한다는 이유만으로 적절한 설계라고 판단할 수는 없다.

기존 프레임워크가 제공하는 기능을 이해하고, 책임의 경계를 구분하고, 불필요한 추상화를 발견할 수 있어야 한다.

그리고 이러한 판단에는 결국 개발자의 기술적 이해와 경험이 필요하다.

## 2. 내가 중요하게 생각하는 것은 책임의 경계다

여러 프로젝트를 경험하면서 시스템 설계에서 가장 중요하게 생각하게 된 것 중 하나가 책임의 경계다.

각 계층이 어떤 역할을 수행해야 하는지, 어떤 책임을 가져야 하는지, 어디까지 의존해야 하는지를 명확하게 구분하려고 노력했다.

예를 들어 Spring 기반 시스템이라면 다음과 같은 구분이다.

| 영역 | 주요 책임 |
|---|---|
| Security | 인증, 인가, 보안 컨텍스트 |
| Controller | HTTP 요청·응답 처리 |
| Application Service | 유스케이스와 트랜잭션 조율 |
| Domain / Entity | 도메인 상태와 비즈니스 규칙 |
| Repository | 데이터 영속화 |
| Infrastructure | 외부 시스템 및 기술적 구현 |
| Audit | 사용자 행위 및 변경 이력 기록 |

물론 모든 프로젝트가 반드시 동일한 계층 구조를 가져야 하는 것은 아니다.

DDD를 적용한 시스템과 단순 CRUD 중심의 시스템은 적절한 설계가 다를 수 있다.

엔티티 내부에 비즈니스 로직이 많다는 것 자체도 잘못된 설계는 아니다.

내가 중요하게 생각하는 것은 특정 패턴을 무조건 적용하는 것이 아니라, **한 번 정한 책임의 기준을 프로젝트 전체에서 일관되게 유지하는 것**이다.

인증된 사용자 정보를 관리하는 책임이 Security에 있다면 다른 계층에서 동일한 인증 로직을 반복할 이유가 적다.

도메인 상태 변경을 엔티티가 책임진다면 동일한 상태 변경 규칙을 여러 서비스에 분산시킬 필요도 없다.

이렇게 책임의 경계가 명확하면 시스템의 변경 영향 범위를 예측하기 쉬워진다.

새로운 요구사항이 들어왔을 때도 어디를 수정해야 하는지 판단하기 쉬워진다.

나는 이것이 장기적인 유지보수성과 개발 생산성에 직접적인 영향을 준다고 생각한다.

## 3. 코드 컨벤션은 단순한 코딩 스타일이 아니다

최근 기존 프로젝트의 코드를 살펴보면서 과거에 고민했던 문제를 다시 떠올리게 되었다.

프로젝트 자체는 코드 컨벤션과 설계 원칙을 중요하게 생각하고 있었다.

하지만 실제 구현을 살펴보니 같은 성격의 개념을 어떤 곳에서는 static 상수로, 다른 곳에서는 enum으로 관리하는 등 구현 방식에 차이가 있었다.

공통 처리 영역에서도 필터와 각 계층의 책임이 서로 다른 방식으로 구성된 부분들이 눈에 들어왔다.

물론 일부 코드만 보고 프로젝트 전체의 설계를 판단할 수는 없다.

기존 시스템에는 그 구조가 만들어진 이유와 당시의 제약이 있을 것이다.

나 역시 기존 프로젝트에 참여하는 입장에서는 현재 구조를 존중하고, 그 구조에 맞춰 기능을 구현하는 것이 우선이라고 생각한다.

그럼에도 아쉬운 부분은 있었다.

**설계 원칙을 중요하게 생각하는 것과 그 원칙이 실제 코드에서 일관되게 유지되는 것은 다른 문제이기 때문이다.**

코드 컨벤션이라고 하면 흔히 네이밍, 들여쓰기, 포맷팅 등을 떠올린다.

하지만 내가 생각하는 코드 컨벤션은 조금 더 넓다.

### Style Convention

변수명, 메서드명, 패키지 구성, 코드 포맷 등 표현 방식의 일관성.

### Architecture Convention

계층별 책임, 의존성 방향, 공통 처리 영역, 인증과 예외 처리의 위치 등 설계 구조의 일관성.

### Implementation Convention

동일한 성격의 요구사항을 어떤 구현 패턴으로 해결할 것인지에 대한 일관성.

이 세 가지가 함께 유지되어야 프로젝트 전체에서 일관된 코드가 만들어질 수 있다고 생각한다.

개발자가 컨벤션을 알고 있다는 것만으로는 충분하지 않다.

AI에게 컨벤션을 설명하는 것만으로도 충분하지 않다.

**실제 구현 과정에서 그 기준을 반복해서 적용할 수 있는 환경이 필요하다.**

## 4. 그래서 템플릿 기반 원셋(One Set)을 만들었다

초기에는 AI에게 더 상세하게 설명하면 해결할 수 있을 것이라고 생각했다.

하지만 프롬프트를 길게 작성한다고 해서 항상 더 좋은 구조가 만들어지는 것은 아니었다.

어떤 계층에서 구현해야 하는지, 어떤 패턴을 사용해야 하는지, 기존 기능을 재사용해야 하는지까지 매번 설명하는 것은 비효율적이었다.

더구나 같은 설명을 제공하더라도 작업마다 구현 방식이 달라질 수 있었다.

그래서 접근 방식을 바꿨다.

**AI에게 매번 좋은 구조를 만들어 달라고 요청하는 대신, 내가 직접 설계하고 검증한 구조를 AI가 활용하도록 만들었다.**

이를 위해 아키텍처, 공통 구현 패턴, 계층별 책임, 코드 컨벤션 등을 템플릿으로 구성했다.

예를 들어 다음과 같은 기준이다.

- 인증과 인가는 어떤 구조에서 처리하는가?
- 사용자 정보는 어떤 방식으로 관리하는가?
- Controller와 Service는 각각 어떤 책임을 갖는가?
- DTO와 Entity의 역할은 어떻게 구분하는가?
- 예외 처리와 공통 응답은 어떻게 구성하는가?
- 외부 API 연동과 트랜잭션 경계는 어떻게 관리하는가?
- 새로운 기능은 어떤 패키지와 진입점에서 시작하는가?

이러한 공통 구조를 하나의 기준으로 정리했다.

내가 말하는 원셋(One Set)은 단순히 동일한 코드를 복사해서 사용하는 템플릿이 아니다.

**프로젝트 전체에서 일관되게 적용할 아키텍처와 구현 규칙의 기준 집합**에 가깝다.

AI가 새로운 기능을 개발할 때 매번 공통 구조를 다시 설계할 필요가 없도록 만든 것이다.

그리고 여기서 가장 중요한 부분은 템플릿 자체가 아니다.

그 안에 어떤 설계 판단이 담겨 있는가이다.

잘못 설계한 템플릿을 사용하면 잘못된 구조가 일관되게 반복될 뿐이다.

따라서 템플릿을 구성하는 과정에서는 직접 코드를 검수하고, 책임을 나누고, 불필요한 추상화를 제거하는 작업을 반복했다.

내가 경험을 통해 판단할 수 있는 좋은 구조를 AI도 사용할 수 있도록 만드는 과정이었다.

## 5. 구조는 표준화하지만, 유스케이스는 열어둔다

여기서 오해하지 않았으면 하는 부분이 있다.

**템플릿 기반 하네스는 AI의 구현 능력을 제한하기 위해 만든 것이 아니다.**

아키텍처와 공통 구현 패턴을 표준화한다고 해서 모든 비즈니스 로직까지 정해진 형태로 구현해야 하는 것은 아니다.

내가 고정하려는 것은 시스템의 책임 경계와 공통적인 설계 기준이다.

반면 실제 유스케이스의 구현은 열어둔다.

예를 들어 특정 데이터를 처리하는 기능이 필요하다면, 그 기능이 어느 계층에 위치하고 어떤 인터페이스를 통해 연결되어야 하는지는 이미 정의되어 있을 수 있다.

하지만 내부에서 어떤 알고리즘을 선택할지, 데이터를 어떻게 효율적으로 처리할지, 어떤 예외 상황을 고려할지는 요구사항과 AI의 판단에 따라 달라질 수 있다.

이렇게 하면 두 가지를 동시에 확보할 수 있다.

**아키텍처의 일관성과 구현의 유연성이다.**

이 구조는 AI 모델의 발전을 활용하는 데에도 의미가 있다.

AI 모델은 계속 발전하고 있다.

새로운 모델이 등장하면 기존 모델보다 복잡한 요구사항을 더 정확하게 이해하거나, 더 효율적인 알고리즘을 제안하거나, 예외 상황을 더 폭넓게 고려할 수 있다.

내 하네스는 이러한 발전을 막지 않는다.

오히려 공통 구조를 다시 설계하는 데 불필요한 판단을 소모하지 않고, 모델의 향상된 능력을 실제 유스케이스 구현에 활용하도록 구성한 것이다.

물론 모델을 변경하면 템플릿 준수 여부와 구현 품질을 다시 검증해야 한다.

하지만 모델이 바뀔 때마다 아키텍처 전체를 새롭게 정의할 필요는 없다.

**설계의 기준은 유지하면서, 구현의 품질은 AI 모델의 발전과 함께 개선할 수 있는 구조.**

이것이 내가 지향하는 템플릿 기반 하네스의 중요한 특징이다.

## 6. 하네스 구축이 어렵지, 이후 개발이 어려운 것은 아니다

내 개발 방식에서 가장 많은 노력이 들어가는 부분은 개별 기능 개발이 아니다.

**초기 하네스와 템플릿을 설계하고 검증하는 과정이다.**

처음에는 상당히 많은 판단이 필요하다.

어떤 기능을 공통화할 것인지, 어떤 패턴을 표준화할 것인지, 어느 영역을 템플릿으로 고정할 것인지, 어느 영역을 유연하게 유지할 것인지 결정해야 한다.

그리고 그 기준이 실제 프로젝트에서도 유효한지 직접 검증해야 한다.

나는 이 과정에서 코드를 상당히 많이 읽고, 검수하고, 수정한다.

단순히 AI가 생성한 결과물을 승인하는 것이 아니다.

왜 이런 구조가 필요한지, 다른 방식이 더 적절하지 않은지, 프레임워크의 기능을 중복 구현하지 않았는지까지 검토한다.

하지만 이 작업이 끝나면 이후 개발 방식은 크게 달라진다.

새로운 기능이 필요할 때마다 공통 구조를 다시 설계할 필요가 줄어든다.

AI는 이미 검증된 템플릿을 기반으로 필요한 유스케이스를 구현한다.

코드가 추가되더라도 기존 프로젝트의 구현 패턴과 자연스럽게 연결되도록 유도할 수 있다.

물론 모든 작업이 자동으로 완벽해지는 것은 아니다.

새로운 요구사항이 기존 템플릿의 범위를 벗어나면 추가 설계와 검증이 필요하다.

하지만 반복적으로 발생하는 구조적 판단의 상당 부분을 재사용할 수 있다.

**초기에 설계와 검증에 집중적으로 투자하고, 이후 개발에서 그 결과를 반복해서 활용하는 방식이다.**

나는 이것이 템플릿 기반 하네스의 가장 실질적인 생산성이라고 생각한다.

---

## 7. 문서 인덱싱과 명확한 진입점은 장기적인 토큰 비용도 줄인다

AI를 활용한 개발에서는 코드 생성 능력만큼 컨텍스트 관리도 중요하다.

프로젝트가 커질수록 AI가 참고해야 하는 코드와 문서도 늘어난다.

명확한 진입점이 없다면 AI는 작업할 때마다 관련 코드를 광범위하게 탐색해야 할 수 있다.

이미 결정된 아키텍처를 다시 분석하거나, 공통 구현 패턴을 찾기 위해 여러 파일을 반복해서 읽을 수도 있다.

이러한 과정은 토큰 사용량과 작업 시간에 영향을 준다.

그래서 하네스를 구성할 때 문서 기반 인덱싱과 진입점 설계에도 신경 썼다.

아키텍처, 구현 패턴, 설계 결정, 작업 이력 등을 문서화하고, AI가 필요한 정보를 찾을 수 있도록 연결했다.

새로운 작업을 시작할 때 프로젝트 전체를 처음부터 읽는 대신, 관련 문서와 코드로 접근할 수 있도록 구성한 것이다.

이렇게 하면 AI가 탐색해야 하는 범위를 줄일 수 있다.

여기서 중요한 것은 단순히 프롬프트를 짧게 만드는 것이 아니다.

**AI가 어떤 정보를 먼저 확인해야 하고, 어떤 범위에서 작업해야 하는지를 명확하게 만드는 것**이다.

프로젝트가 장기화될수록 이 차이는 더 중요해질 수 있다.

초기 하네스 구축에는 많은 노력이 들어가지만, 반복 개발 과정에서는 공통 구조에 대한 재설명과 불필요한 탐색을 줄일 수 있다.

결과적으로 코드 일관성뿐 아니라 컨텍스트 관리와 토큰 사용량 측면에서도 이점을 기대할 수 있다.

물론 실제 절감 효과는 프로젝트 규모와 작업 유형, 모델에 따라 달라질 것이다.

하지만 내가 지향한 것은 분명하다.

**AI가 더 적은 맥락으로도 필요한 작업을 정확하게 수행할 수 있도록 개발 환경을 구성하는 것**이다.

---

## 8. AI를 잘 활용하려면 개발자의 기본기가 필요하다

이러한 경험을 통해 오히려 더 강하게 느끼게 된 것이 있다.

AI가 발전할수록 개발자의 기술적 이해가 불필요해지는 것이 아니라, 그 이해를 활용하는 방식이 달라진다는 점이다.

AI가 코드를 작성할 수 있다고 해서 개발자가 시스템 구조를 몰라도 되는 것은 아니다.

코드가 동작하는 것과 좋은 구조로 구현된 것은 다르기 때문이다.

개발자는 AI가 작성한 코드에 대해 적어도 다음과 같은 판단을 할 수 있어야 한다고 생각한다.

- 왜 이 구조가 필요한가?
- 기존 프레임워크에서 제공하는 기능으로 해결할 수 없는가?
- 해당 기능은 올바른 계층에 위치하는가?
- 책임이 중복되거나 불필요하게 분산되어 있지는 않은가?
- 새로운 추상화가 실제 문제를 해결하는가?
- 장기적인 변경과 운영에도 적합한가?

이런 판단을 하려면 결국 기술을 이해하고 있어야 한다.

나 역시 처음부터 모든 것을 알고 있었던 것은 아니다.

여러 시스템을 설계하고 개발하고 운영하면서 문제가 발생했고, 그 문제를 해결하는 과정에서 설계 기준을 만들어 왔다.

그 경험을 통해 얻은 기준을 템플릿에 담았다.

**내가 알고 있는 좋은 설계 방식을 AI도 활용할 수 있도록 만든 것이다.**

이는 개발자의 전문성을 AI로 대체하는 접근이 아니다.

오히려 개발자의 전문성을 반복해서 활용할 수 있도록 만드는 접근에 가깝다.

AI 모델이 발전할수록 더 많은 구현을 맡길 수 있을 것이다.

하지만 어떤 구조를 유지해야 하는지, 무엇을 변경해야 하는지, 어떤 기술적 선택이 적절한지 판단하는 일은 여전히 중요하다.

그리고 나는 그 판단을 할 수 있는 기본기가 AI 기반 개발에서도 중요하다고 생각한다.

---

## 9. 좋은 코드를 만드는 것보다 좋은 구조가 반복되도록 만드는 것

최근 기존 프로젝트의 코드를 살펴보면서 다시 한번 느꼈다.

프로젝트가 성장하면서 여러 개발자가 참여하고, 다양한 요구사항을 처리하다 보면 구현 방식에 차이가 생길 수 있다.

이는 자연스러운 현상이기도 하다.

하지만 프로젝트 전체의 일관성을 유지하려면 단순히 컨벤션을 정하는 것만으로는 부족할 수 있다.

그 기준이 실제 구현 과정에서도 지속적으로 적용될 수 있어야 한다.

나는 이 문제를 해결하기 위해 템플릿 기반 하네스를 선택했다.

아키텍처와 책임 경계를 표준화하고, 검증된 공통 구현 패턴을 재사용하며, 문서 인덱싱을 통해 AI가 명확한 진입점에서 작업하도록 구성했다.

동시에 유스케이스의 구현은 열어두어 AI 모델의 발전과 새로운 기술적 선택을 활용할 수 있도록 했다.

이 과정에서 가장 어려운 것은 AI에게 코드를 작성시키는 일이 아니었다.

**어떤 구조가 좋은 구조인지 판단하고, 그 구조를 반복해서 활용할 수 있도록 만드는 일이었다.**

나는 AI가 모든 설계 판단을 대신해야 한다고 생각하지 않는다.

그렇다고 개발자가 모든 코드를 직접 작성해야 한다고 생각하지도 않는다.

개발자는 아키텍처의 방향과 책임 경계를 설계하고, AI는 그 구조 안에서 구현 능력을 발휘할 수 있다.

새로운 요구사항이 기존 설계의 범위를 벗어나면 다시 검토하고, 필요한 경우 템플릿과 설계 기준을 발전시키면 된다.

내가 생각하는 하네스 엔지니어링은 단순히 AI에게 지시를 잘 내리는 기술이 아니다.

**개발자의 경험과 설계 지식을 AI가 반복적으로 활용할 수 있도록 개발 환경 자체를 설계하는 일**이다.

좋은 코드를 한 번 작성하는 것도 중요하다.

하지만 장기적으로는 좋은 구조가 반복해서 만들어지는 환경을 구축하는 것이 더 중요하다고 생각한다.

---

### 마치며

AI는 앞으로도 더 좋은 코드를 작성하게 될 것이다.

더 복잡한 유스케이스를 이해하고, 더 나은 알고리즘을 선택하고, 더 많은 구현을 자동화할 수 있을 것이다.

나는 이러한 발전을 적극적으로 활용하고 싶다.

다만 AI 모델이 바뀔 때마다 프로젝트의 구조와 구현 방식이 함께 흔들리는 것은 원하지 않는다.

그래서 구조는 표준화하고, 구현은 열어두었다.

초기에는 많은 시간을 들여 설계하고 검증하지만, 이후에는 그 기준을 재사용하면서 일관된 코드를 만들어 나간다.

**AI에게 더 좋은 코드를 작성하라고 반복해서 설명하는 대신, 좋은 구조를 먼저 만들어 AI가 그 안에서 능력을 발휘하도록 한다.**

그것이 내가 바이브코딩을 경험하며 템플릿 기반 하네스를 구축하게 된 이유다.
