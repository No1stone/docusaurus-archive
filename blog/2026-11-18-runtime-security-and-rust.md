# PHP 다음은 Node.js, 이번에는 Java였습니다

최근에는 기능을 만드는 일 사이로 실행 환경의 보안 공지를 확인하는 일이 이어졌습니다.
Nextcloud의 PHP를 확인하고, Docusaurus를 빌드하는 Node.js를 올리고, 이번에는 Spring 서버가 사용하는 Java 버전을 살펴봤습니다.

각각의 시스템을 따로 만들었는데, 운영하는 사람의 할 일 목록에는 결국 함께 올라옵니다.
코드를 고치지 않아도 확인하고 바꿔야 하는 것들이 계속 생깁니다.

그러다 관심을 두고 읽어 왔던 Rust 관련 글들이 다시 생각났습니다.
AI가 낯선 언어의 구현을 도와줄 수 있다면, 앞으로는 어떤 기반을 선택하는 게 좋을까요.
구현할 수 있다는 것과, 그 선택이 효율적이라는 것은 얼마나 가까울까요.

## 업데이트 하나에도 확인할 대상이 달랐습니다

Nextcloud에서는 PHP만 따로 바꾸고 끝낼 수 없었습니다.
애플리케이션 버전과 함께 업그레이드 경로를 따라가고, 데이터베이스 갱신과 앱 호환성을 확인해야 했습니다.
그 과정은 [Nextcloud 업그레이드 기록](/blog/nextcloud-php-security-upgrade-retrospective)에 남겼습니다.

Docusaurus에서는 Node.js가 사용되는 위치부터 구분했습니다.
배포된 정적 파일을 제공하는 환경과, 사이트를 빌드하거나 개발 서버를 실행하는 환경은 달랐습니다.
로컬의 mise 설정, CI 설정, 프로젝트의 Node 버전 조건을 맞춘 과정은 [Node.js 업데이트 기록](/blog/static-site-node-upgrade-three-places)에 정리했습니다.

이번 Java 확인에서는 Dockerfile의 메이저 버전 표기만으로 실제 실행 버전을 판단할 수 없다는 점이 눈에 들어왔습니다.
같은 태그를 사용해도 이미지를 받은 시점에 따라 내용이 달라질 수 있고, 새 이미지를 받아도 기존 프로세스가 자동으로 바뀌지는 않습니다.
[Docker 이미지 버전 고정](/docs/knowledge/infrastructure/docker/image-tags-and-digest-pinning)과 [사용자 경로의 JDK를 사용하는 JAR 배포](/docs/knowledge/tooling/ci/jar-deployment-with-user-jdk)를 따로 정리한 이유입니다.
이 글을 쓰는 시점에는 수정 릴리스와 적용 절차를 확인했으며, 실제 서버의 Java 교체와 배포 완료까지 검증한 상태는 아닙니다.

| 대상 | 제가 확인했던 중심 질문 |
|---|---|
| Nextcloud와 PHP | 애플리케이션과 실행 환경을 어떤 순서로 올려야 하나요? |
| 정적 사이트와 Node.js | Node.js가 실제로 실행되는 곳은 어디인가요? |
| Spring 서버와 Java | 지금 실행 중인 프로세스는 어느 JDK를 사용하나요? |

보안 공지에 등장하는 기술 이름은 달라도, 제 시스템에서 영향을 받는 경로를 찾는 일은 매번 필요했습니다.
이때부터 언어의 안전성과 운영 기반의 유지보수를 함께 생각하게 됐습니다.

## Rust에 관심이 가지만, 전환의 기준은 더 많았습니다

Rust에 관심을 갖게 된 계기가 이번 보안 공지만은 아닙니다.
관련 글을 읽으면서 소유권과 메모리 관리 방식이 흥미로웠고, AI의 도움을 받으면 직접 시도해 볼 수 있겠다는 생각도 했습니다.

Rust는 소유권 규칙으로 가비지 컬렉터 없이 메모리 안전성을 제공하는 언어입니다.
다만 unsafe 코드와 외부 코드 연동에는 별도의 안전성 검토가 필요합니다.
이 범위는 [Rust 공식 문서의 소유권 설명](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html)과 [unsafe Rust 설명](https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html)에서도 구분합니다.

이 장점은 충분히 매력적입니다.
그렇다고 지금 사용하는 서버를 옮기는 판단까지 바로 이어지지는 않았습니다.
제 서버에는 이미 업무 코드와 함께 인증, 공통 예외, 응답 형식, 감사 필드, 로깅, 데이터 접근 규칙이 쌓여 있기 때문입니다.

처음부터 Rust로 만드는 서비스라면 필요한 기능과 라이브러리를 고르면서 출발할 수 있습니다.
기존 Spring 서버를 옮긴다면, 현재 기대하는 동작이 새 조합에서도 유지되는지 확인해야 합니다.
두 작업은 출발점부터 다릅니다.

## 제가 Spring에 맡기는 것은 코드만이 아닙니다

Spring에서는 인터페이스를 구현하거나 설정을 추가하는 것으로 많은 기능을 사용합니다.
Repository를 호출하고, 트랜잭션 경계를 선언하고, 공통 예외를 응답으로 변환합니다.
그 아래의 모든 코드를 직접 읽고 사용하는 것은 아닙니다.

이런 개발이 가능한 이유 중 하나는 공식 프로젝트의 유지보수 체계를 신뢰하기 때문입니다.
제가 Spring을 선택하는 큰 이유도 여기에 있습니다.

Spring은 데이터 접근, 보안, 메시징 등 여러 영역의 공식 프로젝트를 제공하며, Spring Boot는 지원 버전과 지원 정책을 공개합니다.
다만 Boot가 지원 중이라고 모든 외부 의존성까지 지원 중인 것은 아니므로, 사용하는 라이브러리의 수명도 함께 확인해야 합니다.
공식 [프로젝트 목록](https://spring.io/projects)과 [Spring Boot 지원 정책](https://github.com/spring-projects/spring-boot/wiki/Supported-Versions)이 판단할 출발점을 제공해 줍니다.

제 입장에서는 기능을 호출하는 방법 외에도, 문제가 생겼을 때 확인할 문서와 수정 버전, 업그레이드 방향이 있다는 점이 중요합니다.
공식적으로 관리되는 기반 위에서 제가 맡을 책임의 범위를 정할 수 있기 때문입니다.

물론 그 신뢰가 제 서비스의 정합성까지 보장해 주지는 않습니다.
트랜잭션을 어디서 시작할지, 실패를 어떻게 처리할지, 어떤 동작을 테스트할지는 여전히 제가 정해야 합니다.
그래도 기반 기능의 유지보수를 전부 제 몫으로 떠안는 것과는 부담이 다릅니다.

Rust에서도 제가 필요한 영역을 일관되게 통합하고, 호환성과 보안 패치, 업그레이드 경로를 꾸준히 관리하는 체계가 충분한 신뢰를 준다면 도입할 이유는 더 커질 것입니다.
그 체계가 반드시 Spring과 같은 모양이어야 한다는 뜻은 아닙니다.
제가 맡길 수 있는 책임이 어디까지인지 판단할 수 있어야 한다는 뜻입니다.

## AI로 만들 수 있다면, 만드는 게 효율적일까요

AI에게 기존 기능을 설명하고 다른 언어로 구현해 달라고 요청할 수 있습니다.
컴파일 오류를 수정하고 테스트를 추가하는 과정도 도움받을 수 있습니다.

그런데 그 결과를 운영할 생각을 하면 질문이 달라집니다.
Spring이 제공하던 동작을 새 라이브러리가 어디까지 제공하는지, 직접 만든 부분은 앞으로 누가 관리할지 확인하게 됩니다.

| 확인할 영역 | 이전 후에도 답할 수 있어야 하는 질문 |
|---|---|
| 데이터 접근 | 커넥션이 부족하거나 쿼리가 실패하면 어떻게 처리하나요? |
| 트랜잭션 | 어느 작업까지 함께 성공하거나 롤백되나요? |
| 인증과 감사 | 사용자 정보가 어떤 경로로 전달되고 기록되나요? |
| 예외와 응답 | 실패 원인이 호출부와 운영 로그에 어떻게 남나요? |
| 외부 연동 | 타임아웃과 재시도가 중복 실행을 만들지는 않나요? |
| 유지보수 | 의존성 변경이나 보안 패치 후 무엇을 검증하나요? |

Spring 내부 코드를 전부 알아야 이전할 수 있다는 뜻은 아닙니다.
제가 의존하는 동작과 실패 조건을 알고, 새 구현이 그것을 만족하는지 판단할 수 있어야 합니다.

AI가 구현해 준 양이 커질수록 그 판단에 드는 비용도 함께 봐야 합니다.
설명하고, 코드를 읽고, 검증하고, 잘못된 가정을 수정하는 시간과 토큰 사용량까지 포함하면, 생성된 코드의 양만으로 효율을 말하기 어렵습니다.

지금 제 Spring 기반을 전부 대체하는 선택에는 아직 조심스럽습니다.
다만 이 판단을 계속 유지할지는 모르겠습니다.
Rust 생태계와 도구가 발전하고 제가 확보한 경험이 늘면, 같은 기능을 만드는 비용도 달라질 수 있습니다.
그 변화가 생각보다 빠를 수 있다는 기대도 있습니다.

## SDD를 하면서 다시 생각한 통제의 범위

명세를 먼저 정하고 AI에게 구현을 맡기는 개발을 살펴보면서도 비슷한 고민이 생겼습니다.
기대 동작과 통과 기준을 충분히 적으면, 구현은 어디까지 몰라도 괜찮을까요.

저 역시 Spring 내부 전체를 이해하지는 못한 채 사용합니다.
그래서 내부를 전부 모른다는 사실 자체를 문제라고 보기는 어렵습니다.
대신 제가 신뢰하는 기반의 경계와, 직접 관리해야 하는 코드의 경계를 구분하고 싶습니다.

AI가 만든 구현에서도 장애 위치를 찾고, 수정 범위를 가늠하고, 결과를 검증할 수 있다면 맡길 수 있는 범위가 넓어질 것입니다.
반대로 테스트가 통과했다는 사실 외에는 설명할 수 없는 부분이 계속 쌓인다면, 이후 변경을 맡기는 일도 불안해질 것 같습니다.
명세에는 빠진 조건이 있을 수 있고, 운영에서는 그 조건을 뒤늦게 마주칠 수도 있기 때문입니다.

제 원셋과 경계 규칙을 유지하려는 이유도 이 고민과 연결됩니다.
반복되는 구현을 줄이면서도, 문제가 생겼을 때 어느 유즈케이스와 포트, 어댑터를 살펴볼지 예상할 수 있게 하고 싶습니다.
SDD를 붙이더라도 그 가시성은 계속 가져가고 싶습니다.

아직 블랙박스에 가깝게 맡기는 개발이 어느 범위까지 효율적일지 답을 내리지는 못했습니다.
서비스의 성격과 검증 수단, 사용하는 기반의 유지보수 체계에 따라 답이 달라질 것 같습니다.

당장은 익숙한 Spring 기반을 관리하면서 Rust를 공부하고, 경계가 작은 기능부터 직접 만들어 보고 싶습니다.
그때는 구현이 됐다는 결과와 함께, 제가 어디까지 이해하고 고칠 수 있었는지도 기록해 보려 합니다.

## 자주 묻는 질문

### 이번 Java 확인에서 실제로 서버까지 교체했나요?

이 글을 쓰는 시점에는 수정 릴리스와 적용 절차를 확인했고, 실제 서버의 Java 교체와 배포 완료까지 검증한 상태는 아닙니다.
절차는 Knowledge의 Docker와 JAR 글에 나눠 두었습니다.

### Docker와 JAR 중 어느 글을 보면 되나요?

컨테이너로 배포하면 [Docker 이미지 버전 고정](/docs/knowledge/infrastructure/docker/image-tags-and-digest-pinning)을, 서버에서 JAR를 직접 실행하면 [사용자 경로 JDK JAR 배포](/docs/knowledge/tooling/ci/jar-deployment-with-user-jdk)를 보면 됩니다.

### 왜 Rust로 바로 옮기지 않나요?

메모리 안전성에는 관심이 있지만, 기존 Spring 서버에 쌓인 인증, 예외, 감사, 데이터 접근 같은 운영 기대를 새 조합에서도 검증할 수 있을지가 전환 기준입니다.
AI로 구현할 수 있다는 것과 운영까지 효율적인지는 별도로 봅니다.
